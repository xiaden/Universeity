# UMD Hatchet v1 Scheduler Dependency Barrier (Plan K live blocker)

## Mental Model
The Universal Media Decomposer runs nine decomposition stages over Hatchet as the SOLE v1 scheduler. Each stage is a durable task; stages have a DAG lineage (STAGE_DEPENDENCIES). The Plan K live blocker is that downstream stage callbacks were dispatched before upstream stages committed — all nine tasks start ~simultaneously, dependents fail-closed with MissingRequiredEvidenceError, and duplicate submissions produce duplicate keys. The submission-time `parent_id` option does NOT create any engine-side parent edge on the pinned pair. BOTH SDK-expressible alternatives are now RESOLVED at engine v0.105.2 source level (verified 2026-08-29): (a) cross-workflow `parent_step_run_id` -> `TriggerWorkflowRequest.parent_task_run_external_id` -> persisted `v1_task.parent_task_external_id` IS DISPROVEN as a dispatch barrier — the child is inserted QUEUED at trigger time and the queue pop has NO parent-completion gate (finding 3); (b) intra-workflow `Workflow.durable_task(parents=[...])` IS engine-VERIFIED as the only real barrier — DAG children are NOT inserted until all parents complete via match conditions (finding 2). The P2-S8 probe as written (prove child not dispatched before parent complete via parent_step_run_id) will FAIL and must route to the registration-time DAG. Registration shape / AT-18 / readiness reconciliation for option 1 remains open.

## Coverage
**Documented:** Hosted evidence (run 33229130339, /tmp/r40528/diag-final dump + logs), SDK 1.38.1 registration/dispatch mechanics, why parent_id/parent_step_run_id are not barriers (now with engine source proof), option-by-option analysis (1/2/3/4), engine-verified intra-workflow DAG barrier, assignment/runtime proof surfaces for v0.105.2, latent proof defects, affected code surfaces.
**Not yet documented:** whether v1_task_events_olap ASSIGNED/STARTED rows appear on the durable-DAG path (hosted probe), durable-task-in-DAG interplay with eviction/durable-run-entry wiring (durable + parents combo unprobed), which id to thread for any future cross-run parent (now moot for the barrier decision). **Closed 2026-08-29:** engine gating for multi-task DAGs (VERIFIED, finding 2), parent_step_run_id gating (DISPROVEN, finding 3), server DAG inference (VERIFIED: triggerWorkflowsCore `isDag = len(regularSteps) > 1`).
**Last extended:** 2026-08-29

## Key Findings

### 1. TriggerWorkflowOptions.parent_id is NOT a dispatch barrier (disproven)
- **Location:** `src/umd/jobs/runner.py:255-258` (threads only the latest direct dependency's run id), `src/umd/jobs/hatchet.py:212-265` (`_real_submit_workflow_run`), SDK `clients/admin.py:223-234,371-412,414-457`, `types/trigger.py:10-27`.
- **What:** `parent_id` maps to `TriggerWorkflowRequest.parent_id` (proto tag 3, internal/services/shared/proto/v1/trigger.pb.go:181); on server v0.105.2 it persisted NOTHING: all 45 v1_task rows have `parent_task_external_id=NULL`, `parent_task_id=NULL`, `dag_id=NULL` (umd-dump.sql:12153-12206); WorkflowRun table EMPTY. Worker log shows all nine stages dispatched within ~450ms and dependents failed MissingRequiredEvidenceError before INGEST COMPLETED (log-worker.txt:19-62, 97-115).
- **Server handler proof (v0.105.2):** `AdminServiceImpl.TriggerWorkflow` (internal/services/admin/server.go:25-34) -> `triggerWorkflowV1` (server_v1.go:31) -> `newTriggerOpt` (server_v1.go:236-286) reads ONLY `req.ParentTaskRunExternalId` (line 253). `req.ParentId` is referenced only in analytics (server.go:28,40) and `ScheduleWorkflow` validation (server.go:166-184); it is never mapped into `WorkflowNameTriggerOpts` for plain triggers.
- **Why it matters:** Any design that claims per-stage submissions with `parent_id` give native barriers is disproven by hosted evidence AND engine source.

### 2. Intra-workflow DAG: ENGINE-VERIFIED as the only real dispatch barrier (v0.105.2)
- **Location:** SDK `runnables/workflow.py:1701-1816` (`Workflow.durable_task(name, schedule_timeout, execution_timeout, parents: list[Task] | None = None, retries, rate_limits, desired_worker_labels, backoff_*, concurrency, wait_for, skip_if, cancel_if, eviction_policy)`; docstring line 1740 "Parents must be defined before their children"; creates `Task(is_durable=True, parents=parents)` at 1791-1810, appends to `_durable_tasks`); `runnables/workflow.py:1412-1520` (`Workflow.task` — same `parents` param); `runnables/workflow.py:363-373` (`tasks` property merges `_default_tasks + _durable_tasks`); `runnables/workflow.py:192-276` (`to_proto` -> v1 `CreateWorkflowVersionRequest(tasks=[task.to_proto(...)])`); `runnables/task.py:159-204` (`Task.__init__`, `self.parents = parents or []`, slot_requests `{"durable": 1}` when is_durable); `runnables/task.py:485-540` (`to_proto` -> `CreateTaskOpts(parents=[p.name for p in self.parents], is_durable=self._is_durable, ...)`).
- **v1 CreateTaskOpts fields (verified dump):** 1 readable_id, 2 action, 3 timeout, 4 inputs, 5 `parents` (repeated string = sibling task readable_ids), 6 retries, 7 rate_limits, 8 worker_labels, 9 backoff_factor, 10 backoff_max_seconds, 11 concurrency, 12 conditions, 13 schedule_timeout, 14 `is_durable`, 15 slot_requests, 16 batch.
- **Registration path (verified):** `worker/worker.py:402` `Worker.start()` -> `register_workflows(self._workflows)` -> `register_workflow(workflow)` (line 346) -> `self._client.admin.put_workflow(workflow.to_proto())` (line 352) — the v1 request. Trigger path: `Workflow.run()` (workflow.py:981-1055) -> `self._client._client.admin.run_workflow(...)` (line 1039) — same admin surface as family A.
- **WorkflowKind.DAG caveat (verified):** `WorkflowKind` (FUNCTION=0, DURABLE=1, DAG=2) exists ONLY in the v0 proto `contracts/workflows_pb2.py` (`CreateWorkflowVersionOpts.kind`, field 13). The v1 `CreateWorkflowVersionRequest` has NO `kind` field — SDK 1.38.1 `put_workflow` CANNOT set kind=DAG; the server INFERS DAG from multi-task topology at trigger time (`triggerWorkflowsCore`: `isDag := len(regularSteps) > 1`, pkg/repository/trigger.go:1082). Expressibility caveat: `client.durable_task` (SDK hatchet.py:924-1050) has NO `parents` param — standalone registrations hardcode `parents=[]`; parents are expressible ONLY inside a `Workflow`.
- **Engine-side verification (v0.105.2, repo-root-relative paths):** `pkg/repository/trigger.go::triggerWorkflowsCore` (790-1648): root steps (`len(step.Parents)==0`, 1217) are inserted directly with `InitialState=QUEUED` (1342). Steps WITH parents (default branch 1388-1498) are **NOT inserted at all** — only `V1MatchKindTRIGGER` event-match conditions per parent via `getParentInDAGGroupMatch(...)` (1422; helper 2059-2196); the child `v1_task` row is created only when the match fires (all parents reach required state). `createDAGs` (1727-1842) writes `v1_dag` + `v1_dag_to_task` with `parent_task_external_id` (`pkg/repository/sqlcv1/dags.sql:23,33,43`). Child input carries `TaskInput.DagParentTaskRunIds` (`pkg/repository/input.go:11-28`, set in `newTaskInput` 50-75). Parent outputs available to children via `ListTaskParentOutputs` (tasks.sql:758+, recursive grandparents) — NOT auto-injected into input; our callback overwrites evidence canonically, so harmless. Completion release: `handleTaskCompleted` (internal/services/controllers/task/controller.go:499-545) -> `notifyQueuesOnCompletion` (1007-1066) -> `SchedulerPartitionTopic NotifyTaskReleased`.
- **Remaining probe scope (narrowed):** durable-task-in-DAG interplay — whether a durable child created via match gets its durable run entry / eviction wiring (separate `DurableEvents`/`durable_events.go` machinery; `handleProcessDurableRunTrigger` controller.go:1133-1181 is for child spawns, NOT DAG matches). P2-S8 probe should use 2 durable tasks + 1 edge, assert child `v1_task` row ABSENT before parent terminal event, then created + `dag_parent_task_run_ids` populated after.
- **Why it matters:** Option 1 = one workflow, nine durable tasks, parents edges, all `STAGE_DEPENDENCIES` edges expressible. Costs: registration shape change, AT-18 wording reconciliation (R19), readiness count semantics (workflows->9 tasks), proof-shape changes (engine-visible-proof.sh Check 2 keys on Workflow.name LIKE 'umd-%' — must become step_readable_id/action-based; one workflow_run_id per DAG vs 9).

### 3. parent_step_run_id -> parent_task_run_external_id: SDK-EXPRESSIBLE, server-side DISPROVEN as a dispatch barrier
- **Location:** SDK `types/trigger.py:6-14` (`ScheduleTriggerWorkflowOptions.parent_step_run_id`), `clients/admin.py:226-227` (maps `parent_step_run_id` -> `TriggerWorkflowRequest.parent_task_run_external_id`), `clients/admin.py:390-427` (`_create_workflow_run_request`: options passed as-is outside a callback; `workflow_run_id`/`step_run_id` contextvars only default inside spawns), `clients/admin.py:414-457` (`run_workflow(workflow_name, input, options=TriggerWorkflowOptions())` -> v0 `WorkflowService.TriggerWorkflow` stub, returns `WorkflowRunRef.workflow_run_id`).
- **Proto facts (verified 2026-08-29):** v1 shared `TriggerWorkflowRequest` (contracts/v1/shared/trigger_pb2.py): 1 name, 2 input, 3 `parent_id`, 4 `parent_task_run_external_id`, 5 child_index, 6 child_key, 7 additional_metadata, 8 desired_worker_id, 9 priority, 10 desired_worker_labels. `parent_id` (field 3) is the metadata-only field the plan proved useless; ONLY `parent_task_run_external_id` populates persisted `v1_task.parent_task_external_id`.
- **Engine-side verification (v0.105.2) — DISPROVEN as a gate:** `newTriggerOpt` (internal/services/admin/server_v1.go:236-286) reads ONLY `req.ParentTaskRunExternalId` (253) -> `GetTaskByExternalId` -> `NewTriggerTaskData` (pkg/repository/trigger.go:2852-2952) sets `ParentExternalId`/`ParentTaskId`/`ParentTaskInsertedAt` (persisted per sqlcv1/tasks.sql:690-692 insert, 738-740 select) -> child inserted DIRECTLY as QUEUED at trigger time (nonDagTaskOpts path, trigger.go:1364-1366). The queue pop `ListQueueItemsForQueue` (pkg/repository/sqlcv1/queue.sql:110-129) filters ONLY tenant_id/queue/id-range/priority — **NO parent-completion predicate**; a child with `parent_task_external_id` set is dispatched regardless of parent state. Empirically consistent: hosted run 33240528692 (45/45 parent fields NULL, FORMAT STARTED before INGEST completed — though that run sent the wrong field).
- **Caveats:** singular parent only; `STAGE_DEPENDENCIES` multi-parent edges would rely on transitive coverage — MOOT since the gate itself does not exist. The P2-S8 probe's core assertion (child not SENT_TO_WORKER/ASSIGNED/STARTED before parent durable complete) CANNOT pass on this pin for independent registrations; it must route to the registration-time DAG (Option 1).

### 4. Engine-visible assignment/runtime proof surfaces (v0.105.2)
- **Location:** `.github/scripts/engine-visible-proof.sh:124-206`; schema from umd-dump.sql:8313-8367 (v1_task), 8501-8523 (v1_task_event), 8561-8601 (v1_task_events_olap), 8730-8751 (v1_task_runtime), 8853-8889 (v1_tasks_olap), 5437 (WorkerAssignEvent).
- **What:**
  - `v1_task_runtime.worker_id IS NOT NULL` = active durable-slot LEASE only; rows cleaned at task completion (after_v1_task_runtime_delete_cleanup_batch_runtime_fn trigger). Post-suite check 3 (`engine-visible-proof.sh:204-206`) fails structurally — this caused the observed `engine-verdicts.txt` FAIL.
  - `v1_tasks_olap.latest_worker_id` is the authoritative long-lived assignment surface (43/45 rows = worker acf81bc6 in the dump) + `readable_status` (enum QUEUED/RUNNING/CANCELLED/FAILED/COMPLETED/EVICTED).
  - `v1_task_event.event_type` enum has NO ASSIGNED/STARTED — only COMPLETED/FAILED/CANCELLED/SIGNAL_CREATED/SIGNAL_COMPLETED. Terminal events prove execution outcomes.
  - `v1_task_events_olap` (has ASSIGNED/STARTED/ACKNOWLEDGED/SENT_TO_WORKER/...) was EMPTY in the dump — unverified on this path.
  - `WorkerAssignEvent` is a legacy table, EMPTY on v0.105.2 — do not require.
  - Worker row (isActive=t, sdkVersion=1.38.1) + worker log rx/finished/failed step run lines = genuine execution.
- **Why it matters:** The proof must correlate workflow_run_id/step_id/action_id across v1_task <-> v1_tasks_olap <-> v1_task_event(task_id) <-> Worker, and must NOT fail on v1_task_runtime.worker_id IS NULL.

### 5. v1_task.input is `{}` on the pin — latent Check-4 scoping defect
- **Location:** `.github/scripts/engine-visible-proof.sh:220-225` (live_job_ids from `input->>'job_id'`); dump v1_task.input = {} for all 45 rows.
- **What:** The engine does not persist the run input into v1_task.input on this path (TaskInput struct input.go:11-28 serializes input/trigger_datas/filter_payload/dag_parent_task_run_ids; dump shows {}); the live-job scoping predicate returns empty -> Check 4 would FAIL after Check 3 is fixed. Fix: carry job_id in `additional_metadata` at submission (runner/hatchet.py change) and scope by `additional_metadata->>'job_id'`, or find the true input surface (StepRun/lookup data — unverified).

### 6. Idempotency keys are already stable across duplicate submissions — the defect is dispatch timing
- **Location:** `src/umd/storage/postgres/job_repository.py:181-266` (canonical_evidence_refs, deterministic tie-break), `src/umd/jobs/manifest.py:167-194` (idempotency material excludes job_id).
- **What:** semantic_event rows 3-4 (replayed=true, canonical_job_id=live-dup, observing_job_id=live-share) prove INGEST/FORMAT keys (…939e/…9374) reused across submissions. The live-dup double-BASIC (r37228, key …95bb vs …81c3) arose because the duplicate BASIC ran AFTER FORMAT committed — different evidence -> different key. A barrier that prevents dependents before upstream commit removes the race; snapshot-at-submission does not (see option 3 below).

### 7. Sync-durable deprecation is tracked debt, not an immediate gate blocker
- **Location:** SDK `runnables/task.py:234-235` (DeprecationWarning removed v2.0.0), `src/umd/jobs/hatchet.py:569`; worker log warns on every registration (log-worker.txt:5-13).
- **What:** Sync durable handlers warn on pin 1.38.1; async conversion must be lockstep with an SDK pin bump and re-verified hosted. Record in plan, do not silently upgrade.

### 8. v1 task API cannot thread parents; parent edges only via the v0-trigger path
- **Location:** SDK `contracts/v1/workflows_pb2.py` `TriggerWorkflowRunRequest` (verified dump): fields 1 workflow_name, 2 input, 3 additional_metadata, 4 priority, 5 desired_worker_labels — NO parent fields. The v1 `AdminService.TriggerWorkflowRun` surface cannot express parent relationships. `run_workflow` (admin.py:414) uses the v0 `WorkflowService.TriggerWorkflow` stub WITH the v1 shared `TriggerWorkflowRequest` (contracts/v1/shared/trigger_pb2.py) — the ONLY SDK 1.38.1 submission surface that carries `parent_task_run_external_id`. `features/runs.py:150` `RunsClient.admin_client()` is the public accessor `_real_submit_workflow_run` already uses.
- **Why it matters:** Any implementation must keep using `runs.admin_client().run_workflow(...)`; switching to a v1 task-trigger API would silently lose the parent field.

### 9. Current UMD submission seam (exact amend points for family A)
- **Location:** `src/umd/jobs/hatchet.py:212-265` (`_real_submit_workflow_run`: builds `_TWOpt(parent_id=parent_id)` at line 260 — the WRONG field per run 33240528692; fail-closed model-fields check at 255-259 tests `"parent_id"`; docstring 226-233 asserts the disproven mapping), `hatchet.py:281-284` (`_SDKSubmissionShim.submit_workflow_run` passthrough), `src/umd/jobs/runner.py:255-258` (parent selection `max(deps, key=STAGE_ORDER.index)` — transitively complete for this DAG; the singular-parent constraint means only the latest direct dep is threadable, which IS sufficient here), `tests/test_hatchet_live.py:1850-1880` (`test_native_parent_barrier_submission_shape` asserts `sub["parent_id"] == by_stage[parent_stage]["run_id"]` — the recording-client kwarg + assertion must become `parent_step_run_id`).
- **Current plan status (2026-08-29):** plan P2-S8 is reopened/PENDING with probe-first wording (parent_step_run_id -> parent_task_run_external_id persistence + dispatch barrier probe; on failure route Support -> R&D -> registration-time WorkflowKind.DAG with CreateWorkflowStepOpts.parents). ## Option analysis (evidence-grounded, decision owned by R&D)

**2026-08-29 COMPLEXITY review verdict** (`artifacts/designs/process/COMPLEXITY-universal-media-decomposer-plan-k-live-hatchet-lineage-barrier.md`): recommends Option 1 (single-workflow DAG) as primary — machinery-minimal, all edges expressible — with two human reconciliations (H1 AT-18 reading, H2 readiness count) and one hosted probe; Option 2 (parent_step_run_id) is highest-risk/least-verified (singular, unproven, upgrade leg = SDK/server pair change with drain/rekey); the probe should stay a diagnostic unless it proves BOTH server-side gating AND multi-parent expressibility. The current Plan K amendment 3 text chooses family A (parent_step_run_id) FIRST pending the P2-S13 probe, with the registration-time DAG as the only approved fallback via Support->R&D->Plan K/DD amendment.

- **Option 1 (single 9-task workflow):** ENGINE-VERIFIED as the only real barrier (match conditions, trigger.go:1388-1498; children not inserted until parents complete). Remaining probe scope: durable-task-in-DAG run-entry/eviction wiring. Costs: registration shape change (Workflow class with 9 durable members), AT-18 proof rewrite (engine-visible-proof.sh Check 2 keys on Workflow.name LIKE 'umd-%' — must become step_readable_id/action-based in the latest version), readiness counting (len(registered_workflows)==9 breaks — count durable tasks = 9), selective-rerun topology (a monolithic workflow re-runs the whole DAG; need a rerun sub-DAG registration reusing the same handlers or engine per-step trigger — unverified).
- **Option 2 (independent registrations + server-side barrier):** UNSATISFIABLE on pin — parent_id disproven, parent_step_run_id DISPROVEN as a dispatch gate (newTriggerOpt sets parent fields but child inserted QUEUED; ListQueueItemsForQueue has no parent-completion predicate). The P2-S8 probe will fail; route to Option 1.
- **Option 3 (submission-time snapshot):** Does not fix the race. Fresh-DAG submissions all happen simultaneously -> dependents snapshot empty/partial -> keys computed with wrong (empty) evidence; a later rerun with real evidence produces DIFFERENT keys -> duplicates + poisoned downstream evidence. Correct only with topologically serialized submission = polling/second-scheduler semantics, prohibited. Rejection in plan P2-S14 stands.
- **Option 4 (pre-claim bounded retry/quarantine):** Server-side task retries (retries=N in durable_task) re-invoke the callback — not client polling, not callback resubmission, no second scheduler. But: probabilistic timing window (schedule_timeout 5m + retries×backoff), MissingRequiredEvidenceError is raised pre-claim (hatchet.py:387 -> job_repository.py:254) and never reaches the executor's quarantine path (stage_execution.py:204-269) — needs explicit transient/permanent classification, bounded retry policy, timeout budget, and hosted proof. Viable fallback, weaker than Option 1.
