## Proposed Approaches

### Turn 1 — RnD-Ideator (T1)
**Date:** 2026-08-25
**Approaches:** A (event-sourced ledger + projections), B (native graph authority — contrarian), C (RDF 1.2 triple-store authority), D (bitemporal immutable DB authority).
**Grounding note:** All four approaches share an immutable-blob layer (OCFL 1.1 object storage, content-addressed keys — never user filenames), the plugin-based modality pipeline (per support-researcher report §2: PyAV/ffmpeg, faster-whisper, pyannote, pysubs2, PaddleOCR/Tesseract, pdfplumber/pypdf, pandoc; AGPL items isolated/license-cared), and the security sandboxing regime (nsjail/bubblewrap + rlimits/cgroups/timeouts, §32). Those are approach-independent and not re-argued below. This turn freshly validates the architecture-defining technologies only; extraction-lib licenses remain as recorded in the upstream research.

### Approach A: Event-Sourced Semantic Ledger with Materialized Projections (CQRS/ES)
**Description:** A single append-only semantic log in PostgreSQL is the sole authority for every semantic fact: each machine assertion, user override, alignment, entity merge/split, edit, lock, and invalidation is an immutable row with a monotonic sequence, transaction-time, optional valid-time, `authority` (MACHINE/USER_OVERRIDE), `confidence`, `generated_by` (pipeline step + model/version + input evidence refs), and a JSONB payload for open extension (typed core + extensible predicates — §36). Blobs live in OCFL content-addressed object storage; sources/segments live in deterministic Postgres tables keyed by stable locators (§9). Everything else — the "current knowledge graph" (Neo4j CE or relational recursive CTE), the vector index (pgvector), the full-text index, and search — is a *projection* rebuilt by replaying the log. Dagster software-defined assets declare the projection DAG (source → segment → per-step artifact); Temporal runs durable workflows; invalidation appends an invalidation record and the projection layer recomputes only affected descendant assets (§16). User overrides are log records with USER_OVERRIDE authority that take precedence at projection-time.
**Requirement coverage:**
- *Provenance:* every assertion row carries evidence refs + generated_by + confidence; the log itself answers "who/what/when/why" (§2, §21); audit API = query over the log; PROV-O-aligned field mapping.
- *Alignment:* typed, confidence-bearing, many-to-many correspondence assertions (CORRESPONDS_TO / ADAPTATION_OF / CONTRADICTS / DERIVED_FROM) link segments across languages/adaptations without merging evidence (§4, §5, §12).
- *Resolution:* MERGE/SPLIT/ALIAS are log records, never destructive graph rewrites; canonical entities are projection-time constructs → merges are literally reversible (§29), every alias path preserved.
- *Editing:* all §15 operations are append-only records; machine output is never silently mutated (§7).
- *Invalidation:* asset-DAG selective recompute; stage-level rerun without re-ingestion (§6, §16).
- *Query:* typed REST primary contract + optional Cypher/GQL on the graph projection + structured provenance in every answer (§17, §18, §19).
- *Jobs:* Temporal durable workflows; per-stage artifact records so a late failure retries without repeating early extraction (§23); restart-safe.
- *Security:* shared OCFL/sandbox regime; only the API layer touches stores; no stored procedures on user input; §32 satisfied across all layers.
**Evidence:**
- LMAX retail trading exchange — event sourcing in production; current state derivable by replaying the durable event journal — https://martinfowler.com/articles/lmax.html
- Parafin (fintech) — "ledger of record": append-only double-entry log as source of truth, product state derived from ledger state, Temporal for idempotent retries — https://www.parafin.com/blog/from-early-stage-shortcuts-to-a-ledger-of-record-our-journey-to-reliable-money-movement
- RISKflo GRC at HSBC — event sourcing + CQRS in production banking, 36,000 events/day, every action an immutable event, point-in-time reconstruction — https://netevo.com.au/case-studies/riskflo/
- Event-sourced audit log (brokerage, SEC/FINRA/MiFID II) — append-only log as single authority + materialized read model (CQRS), hash-chained tamper evidence — https://aquicksoft.com/blog/event-sourced-audit-log
**Technology validation:**
- PostgreSQL 18.6 — current stable (released 2026-08-13; 17.x/16.x also supported; 19 in Beta) — https://www.postgresql.org/docs/release/18.6/ — checked 2026-08-25 — verdict: use 18.x.

Nvidia, Netflix, Snap, Stripe (2026-05); open-source + Cloud compatible; Nexus GA (2025) — https://thenewstack.io/temporal-durable-execution-ai-workflows/ and https://temporal.io/blog/temporal-series-c-announcement — checked 2026-08-25 — verdict: mature, production-proven; ops cost is its known tradeoff.

### Approach B: Mutable Property-Graph Authority (Neo4j CE) with Changelog Mirror (contrarian)
**Description:** The knowledge graph in Neo4j CE *is* the semantic system of record — nodes and edges carry typed properties (assertion, confidence, authority, evidence refs); evidence anchors are first-class nodes linked to semantic nodes by typed edges. History is kept by a sidecar append-only "changelog mirror" in PostgreSQL: every mutating Cypher transaction is recorded (actor, time, reason, before/after deltas) so audit is a replayable delta log rather than the authority. Query = native Cypher/GQL directly on the graph (deep traversal, GDS algorithms, GraphRAG). Search/vector = sidecar index keyed by element IDs. Jobs = Temporal; invalidation = compute the downstream-dependency subgraph in Cypher, then Targetedly rerun the affected alignment/reconciliation sub-workflows. This is the contrarian option: it bets that for graph-shaped semantic QA (§17) the cost of projection lag is worse than the cost of keeping a graph consistent by transaction.
**Requirement coverage:**
- *Provenance:* assertion nodes carry evidence refs + confidence + generated_by; the changelog mirror answers "what did the graph believe / what changed" by delta replay; §2 capability preserved but hand-built.
- *Alignment:* correspondence edges (CORRESPONDS_TO etc.) with confidence properties; many-to-many by construction; §12 fully graph-native.
- *Resolution:* merges must be modeled as first-class relationships (SAME_AS / canonical pointer) or as merge-event nodes, never by deleting mentions — with the changelog mirror providing undo; reversible in principle, requires discipline.
- *Editing:* Cypher mutations + changelog records; overrides as assertion nodes with USER_OVERRIDE authority; §7 respected at the model level.
- *Invalidation:* dependency subgraph queries drive targeted reruns; §16 satisfiable but invalidation logic is custom.
- *Query:* native Cypher/GQL is the strongest traversal surface of all four approaches; structured REST wrapper; §18 trivially met.
- *Jobs:* Temporal durable workflows; per-stage artifacts; §23 met.
- *Security:* Neo4j CE has basic native auth but no RBAC (EE feature) — the API layer must enforce authorization; shared sandbox regime for media parsers.
**Evidence:**
- Prospa (Australian fintech) — Neo4j "serves as Prospa's system of record and most trustworthy source of truth for customer relationships" — https://neo4j.com/customer-stories/prospa/
- BT Group SRIMS — network inventory rebuilt on Neo4j as "one system of record", 3,000 users, 50,000 availability checks/day — https://neo4j.com/customer-stories/bt-group/
- JupiterOne (cybersecurity CAASM) — consolidated all data onto a single Neo4j backend ("data comes in, hits the graph, and is queried"), ingestion lag 8h → 10s, p99 180ms — https://neo4j.com/customer-stories/jupiterone/
- NASA knowledge graph (Lessons Learned + GeneLab/SPOKE fabric) — graph-native knowledge architecture at agency scale — https://neo4j.com/blog/knowledge-graph/nasa-critical-data-knowledge-graph/ and https://ntrs.nasa.gov/api/citations/20250000723/downloads/IWS_GeneLab_Fabric_2025.pdf
**Technology validation:**
- Neo4j CE — GPLv3, single-instance, no clustering/HA/backups (Enterprise-only); ops-manual current 2026.07, LTS 5.26 — https://neo4j.com/docs/operations-manual/current/introduction/ and https://neo4j.com/open-core-and-neo4j/ — checked 2026-08-25 — verdict: viable for single-node deployment; RBAC/HA/licensing are the known ceilings, and the changelog mirror must compensate for the absence of built-in audit features.
- PostgreSQL 18.6 (changelog mirror + segment registry) — validated as in Approach A — checked 2026-08-25.
- Temporal — validated as in Approach A — checked 2026-08-25.
- GQL/Cypher convergence — Neo4j is on the ISO/IEC 39075 GQL trajectory but GQL is still landing across engines; Cypher remains the de-facto surface — label provisional (per upstream research §1.2; no fresh primary source this turn beyond Neo4j docs).
**Feasibility:** MEDIUM — the query story is superb and there is real production precedent for graph-as-record, but provenance/audit/reversible-merge are all hand-built on top of a fundamentally mutable model, and CE's single-node/licensing ceiling is a constraint to plan around.
**Tradeoffs:** Makes easy — native deep traversal (scenes containing X, contradictions between continuities, shortest paths), zero projection lag, intuitive evidence-anchor modeling, GraphRAG-ready. Makes hard — guaranteeing "provenance is never lost" when the authority is mutable (the changelog mirror must be made bulletproof and transactional with Cypher mutations), reversible merges require modeling discipline, no built-in bitemporal/history, EE-only RBAC means authz lives in the API layer, and graph quality is enforced at write time rather than rebuild time.

### Approach C: RDF 1.2 Triple-Store Authority with Triple Terms (Wikidata/OpenCitations-style)
**Description:** The semantic authority is an RDF quad store (GraphDB) using RDF 1.2 *triple terms* — the W3C-standardized statements-about-statements mechanism — so "assertion X has evidence E, confidence C, produced_by step S, authority USER_OVERRIDE" is expressed natively rather than reified by hand. Provenance uses PROV-O; the typed core + extensible predicates (§10, §36) are an open ontology with SHACL shapes for validation and no schema migrations for new predicates. Sources/segments remain in Postgres (deterministic stable locators, §9); blobs in OCFL. Query = SPARQL endpoint plus a typed REST layer compiled to SPARQL (the RAMOSE/OpenCitations pattern). Audit = timestamped named-graph snapshots with delta links (oco:hasUpdateQuery pattern) — change-tracking as first-class RDF. User overrides are triple-term-bearing assertions with precedence predicates. Jobs = Temporal; invalidation = retract/supersede triples and create new snapshots, then trigger dependent recompute workflows.
**Requirement coverage:**
- *Provenance:* the strongest standards story — triple terms literally model claims-about-claims (§2); PROV-O covers wasGeneratedBy/wasDerivedFrom/agent-version; §13 structured model I/O maps to RDF.
- *Alignment:* typed correspondence triples, many-to-many, confidence-bearing (§12); language/adaptation as graph properties, not boundaries (§4, §5).
- *Resolution:* merge = owl:sameAs / canonical-entity triples that can be retracted without destroying mention history; reversible by construction (§29).
- *Editing:* statements carry rank/qualifier/reference/authority — the Wikidata model — so §7 overrides and §15 operations are native "add assertion with precedence" transactions; snapshots preserve history (§21).
- *Invalidation:* supersede + snapshot deltas, then Temporal-driven recompute of dependent steps (§16).
- *Query:* SPARQL 1.2 (suite under development) + typed REST; deterministic structured access with provenance (§17, §18).
- *Jobs:* Temporal; per-stage artifacts; §23 met.
- *Security:* GraphDB supports auth/RBAC (enterprise tier); expose only through API layer; shared OCFL/sandbox regime for media.
**Evidence:**
- Wikidata, the largest production statement+provenance knowledge base — statements with *qualifiers, references (sources), and ranks*, exposed as RDF dumps and SPARQL (WDQS) — https://www.wikidata.org/wiki/Wikidata:Data_model and https://www.wikidata.org/wiki/Help:Statements — the closest large-scale analog to "evidence-bearing claims that must never collapse into one truth".
- OpenCitations — production SPARQL endpoints serving provenance-tracked citation data; RDF change-tracking via named-graph snapshots, PROV predicates, and oco:hasUpdateQuery deltas — https://opencitations.net/querying/ and https://arxiv.org/html/2306.16191 — live proof of RDF provenance/change-tracking at scale.
**Technology validation:**
- RDF 1.2 Concepts & Semantics — W3C Candidate Recommendation Snapshot 2026-04-07; triple terms standardized; not yet advanced to Recommendation as of check (earliest noted 2026-05-05; still CR) — https://www.w3.org/TR/rdf12-concepts/ — checked 2026-08-25 — verdict: implementable now (CR, implementation phase), but treat as evolving; pin to the CR snapshot and track advancement.
- GraphDB 11.5.0 (latest Docker tag) / 11.4.2 (2026-07-20) — mature quad store; 11.2+ added native Python client, SPARQL 1.1 conformance improvements, vector-search connectors, Talk-to-Your-Graph — https://graphdb.ontotext.com/documentation/11.4/release-notes.html and https://hub.docker.com/r/ontotext/graphdb/tags — checked 2026-08-25 — verdict: current; triple-term support assumed via RDF-star lineage (verify exact triple-term conformance against GraphDB docs during design-author step — provisional).
- SPARQL 1.2 — part of the RDF 1.2 suite, still in progress in the W3C RDF & SPARQL WG; GraphDB advertises SPARQL 1.1 conformance — provisional, check advancement in later turns.
- PROV-O / PROV-DM — W3C Recommendations (2013), stable interop vocabulary — https://www.w3.org/TR/prov-o/ — checked 2026-08-25.
- PostgreSQL 18.6 (segments/locators) — validated as in Approach A — checked 2026-08-25.
**Feasibility:** MEDIUM — the data model is the most faithful to the requirements (claims-with-provenance is literally the WD/OpenCitations model), but it introduces a second authoritative store, a younger ecosystem (RDF 1.2 CR), and SPARQL developer friction.
**Tradeoffs:** Makes easy — standards-grade provenance and extensibility without migrations, interop (PROV-O, SHACL, RDF dumps), truthful coexistence of contradictory source claims. Makes hard — keeping Postgres (structural) and the triple store (semantic) transactionally consistent, SPARQL learning curve for the API team, triple-term tooling maturity (CR phase), UI/query ergonomics need additional layers (REST-over-SPARQL), and licensing of a commercial-grade engine (GraphDB free tier constraints must be reviewed).

### Approach D: Bitemporal Immutable Database as Authority (XTDB 2) — buy the time-travel
**Description:** The semantic authority is XTDB 2 (MPL-2.0): every semantic fact, override, alignment, and merge is submitted as a transaction into an append-only log; the engine maintains SQL:2011 bitemporal history (system-time + valid-time) automatically, so as-of queries ("what did the graph believe at T", "what changed between T1 and T2") need no audit tables, triggers, or hand-rolled replay. The structural layer (sources/segments with stable locators) can remain in Postgres, and XTDB 2.2 can ingest it via Postgres logical replication as an external source, mirroring it into bitemporal history. Graph query surface = recursive-CTE SQL over graph-shaped tables (bounded-depth traversal) with an optional Neo4j projection for deep traversal; vector/full-text = pgvector/tsvector sidecar. Jobs = Temporal or Hatchet (Postgres-native, consistent with the Postgres-centric ops story); invalidation = a new transaction supersedes old facts (valid-time end) and change events from the log tail trigger downstream recompute.
**Requirement coverage:**
- *Provenance:* engine-native — every fact is a transaction; system-time answers "what/when", valid-time models narrative/claim currency (§30); audit is a query, not a subsystem (§21).
- *Alignment:* typed fact rows for correspondence, many-to-many, confidence-bearing; valid-time supports scope/continuity (§5, §12).
- *Resolution:* merge/split = retract + assert new facts; all prior facts remain in history → trivially reversible (§29).
- *Editing:* append-only by construction — no in-place UPDATE of history; overrides are new authoritative facts (§7, §15).
- *Invalidation:* log-tail change events + Temporal/Hatchet recompute of dependent steps; §16 satisfiable with per-stage artifacts.
- *Query:* SQL:2011 including FOR SYSTEM_TIME/valid-time syntax; typed REST; RCTE traversal; §18 met for bounded-depth graph queries.
- *Jobs:* Temporal (or Hatchet as the lighter Postgres-native alternative); durable, restartable (§23).
- *Security:* XTDB auth via OIDC (2.1+) / configured root user; no RBAC — enforce at API layer; shared OCFL/sandbox regime.
**Evidence:**
- Nubank (40M+ customer Brazilian fintech) — runs Datomic (immutable, append-only database) as the system of record for double-entry accounting; built-in history gives audit trails, chronological replay for bug recovery, and time-travel without ETL — https://www.datomic.com/nubanks-story.html and https://www.infoq.com/presentations/nubank-architecture/ — the flagship production proof of "immutable time-travel DB as authority".
- XTDB 2.2 release notes — "XTDB in production across a number of client sites"; Postgres logical-replication source, Arrow ADBC/Flight SQL, leader election, GC, pgwire — https://github.com/xtdb/xtdb/releases/tag/v2.2.0-rc0 — checked 2026-08-25.
**Technology validation:**
- XTDB 2.1.0 GA; 2.2.0-rc0 (2026-07-21) — 2.2 adds Postgres external source, ADBC/Flight SQL, GC; breaking auth changes in 2.2 (CREATE USER removed; OIDC recommended); pgwire compatibility targeting the Postgres ecosystem ("reports PG 16") — https://github.com/xtdb/xtdb/releases and https://docs.xtdb.com/quickstart/sql-overview.html — checked 2026-08-25 — verdict: 2.1 line is GA; the 2.2 line (external sources) is RC → label provisional for the Postgres-source feature; core bitemporal/SQL surface is GA.
- Hatchet — durable tasks = "drop-in replacement for Temporal or DBOS"; Postgres as the durability layer; durable-execution revamp merged 2026-03-16 (PR #2954); platform changelog v0.101.27 — https://github.com/hatchet-dev/hatchet and https://docs.hatchet.run/reference/changelog/platform — checked 2026-08-25 — verdict: viable lighter alternative; younger than Temporal, no deterministic code replay (idempotency on the user).
- PostgreSQL 18.6 + pgvector 0.8.6 (structural layer + sidecar indexes) — validated as in Approach A — checked 2026-08-25.
- Temporal — validated as in Approach A — checked 2026-08-25.
**Feasibility:** MEDIUM — the audit/provenance story is the cheapest of all four (engine-native), but it introduces a JVM/Clojure ops surface and a less-mature ecosystem; the 2.2 external-source path is RC, and graph traversal depth is bounded without an added projection.
**Tradeoffs:** Makes easy — time-travel/audit/retroactive reconciliation with zero custom log machinery, append-only by construction, reversal-as-new-transaction, strong SQL tooling compatibility. Makes hard — JVM ops and a newer engine (talent/observability maturity), no native graph traversal (RCTE bounded-depth; deep graph QA needs an added projection), newest feature line (2.2) still RC, and organization novelty risk for an infrastructure cornerstone.

**Summary:** Ranking by fit-to-requirements and risk: **A** is the highest-confidence fit (HIGH feasibility; every hard requirement — provenance, reversible merges, append-only editing, audit, selective invalidation — maps to a structural guarantee; production pattern proven across finance/GRC/audit systems). **C** is the most semantically faithful (claims-with-provenance is its native shape; WD/OpenCitations are direct production analogs) but carries a second authoritative store and CR-phase ecosystem → MEDIUM. **D** buys engine-native bitemporal time-travel and is architecturally distinct from A (delegating the log instead of hand-rolling it) but adds JVM ops and an RC feature line → MEDIUM. **B** is the deliberate contrarian: graph-as-record has real production precedent and the best traversal surface, but provenance/audit/reversible-merge are all hand-built atop a mutable store with a single-node GPLv3 ceiling → MEDIUM and the highest provenance-risk. Recommendation for the Refiner/DD-Author: lead with **A**, keep **C** and **D** as the strongest challengers, and preserve **B** in the record as the tested-against alternative.

### Critique of Approach A: Event-Sourced Semantic Ledger with Materialized Projections (CQRS/ES)

**Findings:**

1. **Schema evolution is the pattern's #1 documented failure mode — and this system *will* hit it.** The only large empirical study of event-sourced systems (19 systems, 25 engineers) identifies event-system evolution, learning curve, rebuilding projections, and data privacy as the recurring production challenges, and — critically — finds **8 of 19 production systems sacrifice immutability by mutating events**, which the authors state means those systems "do not satisfy the goal of a complete audit trail" ([T1] Overeem et al., JSS 2021). This system's §2 ("provenance is never lost") and §21 (audit) are exactly a "complete audit trail" requirement, so the protection cannot be assumed from the pattern — it must be enforced by an explicit event-schema versioning design (versioned events + weak schema → upcasting, per the same study). The Ideator's "strict event-schema versioning discipline" tradeoff is acknowledged but is not optional budgeting — it is the difference between this approach delivering §2 or silently not delivering it.
2. **Dual-write is the specific anti-pattern that breaks rebuildability, and Approach A has three write paths (log → Dagster projections → Neo4j/pgvector/search).** Nat Pryce's postmortem of a production fraud-detection system documents exactly the failure: command handlers recorded events *and* updated the relational state directly, so "there was nothing to ensure that entity state could be rebuilt from the recorded events" ([T1] natpryce.com). Every projection in A must be derived *only* by replaying the log; if any user-override or machine output path writes state directly into the Neo4j/pgvector/search projections (a very tempting shortcut for §7 overrides), the entire "reversible by replay" guarantee dies silently. Related: Dennis Doomen's production experience shows projectors that read from *other* projectors introduce state that cannot be rebuilt cleanly ([T1] dennisdoomen.com) — the §16 dependency graph must be enforced, not assumed.
3. **Replay/rebuild cost is a real operational risk at this system's data shape.** Documented production cases: a financial app's full replay took "minutes" on 3TB of events until snapping/archival; a corrupted projection replay of 2 weeks took 18 hours ([T2] dev.to production war stories). For this system, entity streams are the dangerous shape: Doomen documents a single aggregate accumulating 100K+ events because a background job lacked idempotency ([T1]). Entity aliases/merge/split churn under §29 could produce long entity streams, and §16's selective invalidation means *partial* projection rebuilds — which requires per-stream checkpoints and idempotent handlers (documented requirements, not optional). The Ideator's "per-asset incremental materialization" is the right answer but must include idempotency + checkpointing from day one.
4. **pgvector claim is current — with a security caveat and a documented scale ceiling.** pgvector 0.8.x is production-viable up to roughly 10M vectors (well beyond this project's early corpus) ([T2] selfhost.dev 2026 reality check; thebuild.com). However: **CVE-2026-3172 — a buffer overflow in *parallel HNSW index builds* (0.6.0–0.8.1) that can leak data or crash the backend — was fixed only in 0.8.2 (Feb 2026)** ([T1] thebuild.com). A media decomposer will build exactly these indexes over evidence embeddings, so the deployment must pin ≥0.8.2 (the Ideator's 0.8.6 check is fine but the CVE rationale should be recorded), and HNSW builds need `maintenance_work_mem` in the GB range or they silently fall back to a 10–50× slower disk path ([T2] selfhost.dev). The pragmatic ceiling (10–50M vectors, or heavy write churn vs HNSW maintenance) means the vector store must remain behind a projection interface with a dedicated-vector-DB escape hatch — consistent with A's design, but it should be written down as a growth plan.
5. **Temporal's self-hosting cost is the Ideator's own "known tradeoff" — now quantified, and it bites this workload profile.** Official production checklist ([T1] docs.temporal.io/self-hosted-guide/production-checklist): shard count is configured at build time and **cannot be changed later without a rebuild+migration**; self-hosted Temporal ships **no RBAC and no audit logging out of the box** (both are product requirements here — §33 observability, and a job-execution audit that must not be weaker than the semantic audit); releases land about every two weeks with a required sequential upgrade path; and scaling "takes significant engineering and ongoing effort" (Datadog's four-year self-hosting talk documents cluster-scale incident classes, [T1] temporal.io). Media ingest is bursty (batch uploads → stage-fan-out), and bursty start patterns are a documented failure profile on a Postgres-backed Temporal backend (community report: ~50–200 workflow starts/sec ceiling on Postgres; thundering-herd on burst schedules, [T2] community.temporal.io thread). Not fatal — but the Temporal-vs-Hatchet decision in Approach D's pitch is a real tradeoff, not a tie.
6. **Projection lag meets §21 head-on.** CQRS literature is uniform that reads can be stale in the inconsistency window ([T1] Overeem et al.). §17's "What changed after the user corrected this entity?" and §21's "Why does the graph currently believe X?" must define what "currently" means when the authoritative log is ahead of the materialized graph. The API needs an explicit consistency contract (e.g., read-your-writes tokens per entity, or a documented freshness bound per surface) — the Ideator's design doesn't state one.

**Citations (tiered):**

### Critique of Approach B: Mutable Property-Graph Authority (Neo4j CE) + Changelog Mirror

**Findings:**

**Description (as refined):** Single append-only semantic log in PostgreSQL 18 remains the sole authority for every semantic fact (assertions, overrides, alignments, merges/splits, locks, invalidations) — each row carries monotonic `seq`, `tx_time`, optional `valid_time`, `authority`, `confidence`, `generated_by`, `correlation_id`/`causation_id`, and a versioned JSONB payload. Blobs in OCFL 1.1 object storage; sources/segments in deterministic Postgres tables keyed by stable locators. Every other surface — Neo4j CE graph projection, pgvector vector index, tsvector full-text, search, "current state" — is a projection rebuilt ONLY by replaying the log (single-writer rule below). Dagster declares the projection/DAG freshness metadata; the durable job engine runs stage workflows; invalidation appends a record and recomputes affected assets only.

**Schema versioning/upcasting strategy (concrete artifact):**
- Event envelope: `event_type` (past-tense), `event_version` (int), `payload` JSONB, `schema_url` pointing at a JSON Schema artifact per `type@version` in `schemas/events/{type}/v{n}.json` (checked into repo, reviewed like code).
- Evolution policy matrix (from critique A1 + youngju.dev 2026-03-07 decision matrix + letsbuildsolutions 2026-05-03): additive optional field → weak schema (documented default); rename/split/type change → upcaster; semantic change → new event type; regulatory purge → documented crypto-shred/copy-transform escape hatch, only with explicit approval.
- Upcaster registry: pure functions `(payload, version) -> payload`, chained per type, colocated with the schema artifact (letsbuildsolutions: "keep upcasters colocated with the schema definition"), unit-tested against stored historical event fixtures for every projectable version (the Doomen lesson).
- CI gate: JSON Schema draft backward-compat check (new schema vs previous) fails on renames/removals/type changes; upcaster presence required for any breaking change; contract tests compile consumers against all versions.
- Entity streams: snapshots carry explicit `schema_version`; on mismatch the snapshot is ignored and full replay happens (youngju.dev snapshot anti-pattern #1; Doomen 100K-event-stream lesson) — snapshotting only introduced after a measured problem per the anti-pattern guidance.
- Corrections are themselves events (`CorrectionApplied`), never in-place mutations (matthewpalma.dev 2026-08-15: "correction is itself a new event, not an edit to history").

**Projection single-writer enforcement (test rule):**
- Rule: every projection store is written ONLY by projection builder jobs whose input is the log (replay from a documented position, idempotent UPSERT handlers with checkpointing per projection — youngju.dev projection-rebuild principles: idempotency, checkpointing, blue-green swap, backpressure).
- Enforcement 1 (ACL): projection stores (Neo4j, pgvector, search) are only reachable with credentials held by projection workers; the API read path uses read-only credentials. User overrides and machine outputs are log records and never written directly to any projection.
- Enforcement 2 (module rule): architecture test that fails CI if any module outside `src/projection_builders/*` imports projection-store clients — the single-writer rule is encoded, not policed by memory.
- Enforcement 3 (§34 determinism test): wipe each projection store, replay the log over a fixture corpus, compare checksums to the pre-wipe state. If any non-projection path had written state, this test catches it.
- Rebuild budget: rebuild-time and trigger thresholds documented per projection (e.g., graph projection rebuild budget; blue-green rebuild into a fresh store then atomic swap — youngju.dev).

**Read-consistency contract for §17/§21:**
- History/provenance queries (§21 "why does the graph believe X", "what did it believe at T", "what changed") read the authoritative log directly → always consistent by construction; projections are never asked for history.
- Current-state queries (§17 semantic QA, search) read projections with an explicit contract: every mutating API call returns a `read_your_writes_token` = the committed log `seq`; a request that carries a token waits until every projection touched by that query has applied ≥ token (projection handlers store last-applied global position; wait bounded by the projection's documented lag budget, default target ≤ 500 ms, monitored). Requests without a token are served with a documented freshness bound and a `stale_at` marker in the response envelope (matthewpalma.dev identifies exactly this read-your-writes option; Overeem: CQRS reads are stale in the inconsistency window unless handled).
- §7 overrides appear to end users only after the token gate passes — an override followed by an immediate query never returns the pre-override answer.

**Changes from Turn 1 (responding to critique):**

**Semantics resolution (concrete):**
- Verification, 2026-08-25: GraphDB 11.4 release notes (11.4.2, 2026-07-20) and W3C-specs page still frame the mechanism as RDF-star/SPARQL-star — "an extension of the RDF 1.1 standard" whose embedded triples assert the referenced statement — NOT RDF 1.2 triple terms (which are non-asserting, occur only in object position, and use `rdf:reifies`). GraphDB is built on RDF4J (11.4 bundles RDF4J 5.2.2 per release notes); RDF4J's own tracker (issue #5327, open) confirms RDF 1.2/SPARQL 1.2 support is in progress — spring/summer 2026 work incl. an outside contribution (Bloomberg): triple-term core model (PR #5404), parsers/writers (PR #5836), with MemoryStore targeted first and LMDBStore explicitly deferred. Conclusion: GraphDB 11.5/Docker-latest has NOT established RDF 1.2 triple-term conformance as of 2026-08-25.
- Decision: **pin RDF-star semantics on GraphDB** (embedded triple `<<s p o>>` IS asserted; reifier IRI carries evidence refs, confidence, authority, generated_by). This is semantically adequate for our model: a claim embedded-asserted is "this statement is part of the graph's content as recorded from source S" — truth/preference is a projection over rank/confidence/authority, exactly the Wikidata statement model (qualifiers + references + ranks) and OpenCitations' prov pattern. This also gives the honest framing the critique demanded: the "assert X is asserted with evidence E" statement is the entire point, and RDF-star's asserting semantics matches it directly.
- Fallback engine (license-free, true triple terms): **Apache Jena 6.1.0** (released 2026-05-11; Apache-2.0) — native RDF 1.2 support: triple terms (`StatementTerm`, object-position only per CR), `rdf:reifies`, RDF/XML 1.2, SPARQL 1.2 Query/Update; model API `createReifier` — https://github.com/apache/jena/blob/main/CHANGES.txt and https://jena.apache.org/documentation/javadoc/jena/org.apache.jena.core/org/apache/jena/rdf/model/Model.html — checked 2026-08-25. Selected as fallback if (a) non-asserting quoted claims become a hard requirement or (b) GraphDB EE licensing is rejected; Jena/TDB2 is single-node and smaller-scale than GraphDB EE, which is why it is the fallback, not the primary.
- §34 conformance test: a test that asserts the pinned semantics (embedded triple presence ⇒ assertion; retraction removes it) and fails loudly if the engine behaves differently — pins the contract against engine drift.

**Snapshot/audit rebuilds as first-class operations; abuse controls:**

- Postgres↔triple-store consistency (dual-write answer): the structural layer (sources/segments/locators, §9) stays in Postgres; any assertion referencing a source locator is staged through an **outbox** — assertion row + provenance row in one Postgres transaction, then an idempotent drainer applies it to the triple store (content-addressed inserts / SPARQL ASK-guarded, crash-safe on startup re-run). This is exactly the pattern the production knowledge-service uses (triple_outbox 2PC + startup drainer, outbox docs in its architecture notes — https://github.com/arshadansari27/knowledge-service ) — checked 2026-08-25. The outbox does not make the triple store authoritative-over-Postgres; it makes the bridge crash-safe and idempotent, closing critique C4's §34 "inconsistent data across storage technologies" hole.

### New / remaining concerns

**1. Token-wait budget-exceeded behavior is unspecified (A — read-consistency contract).** The contract says a token-bearing request "waits until every projection touched by that query has applied ≥ token; wait bounded by the projection's documented lag budget." What happens when the wait *exceeds* the budget — block indefinitely (correct but unbounded), fail fast with a retryable 409/503, or serve stale+`stale_at` (which would break the design's own guarantee that "an override followed by an immediate query never returns the pre-override answer")? During a large scheduled invalidation-rebuild (§16), projection catch-up can be minutes, not 500 ms. *Why it matters here:* §7 override flow is exactly the path that must never silently serve stale truth, and media-corpus rebuilds are the multi-minute case. *Severity:* MEDIUM — a spec hole, not a design failure; closes in one decision.
**Citations:** T2: older youngju.dev projection principles already cited by Ideator (idempotency/checkpoint/blue-green) — machinery exists; the decision is API-behavior policy, no new evidence needed. (Speculative label: no documented failure found for "token-lag budget" because the pattern is the team's own invention; flagging undefined behavior, not a broken one.)

**2. Hatchet quantity needs recalibration; durable-execution is the youngest component in the stack (A — job engine decision).** Verified against current official docs (2026-08-25):
- **"A single engine instance with PostgreSQL-only storage typically handles hundreds of tasks per second"** — and throughput only scales up with RabbitMQ added as the message queue and "through tuning and sharding" ([T1] https://docs.hatchet.run/guarantees-and-tradeoffs). The 10k/s figure comes from vendor benchmarks on an **m7g.8xlarge RDS instance** (32-vCPU class) with a tuned config; 2000/s was the sustained number on m7g.2xlarge at ~83% DB CPU ([T1] https://docs.hatchet.run/self-hosting/benchmarking — methodology public via the `hatchet-loadtest` container, reproducible but vendor-published). The T3 statement "load-tested to 10k tasks/sec" is *true but context-dependent*; the honest baseline for this project's self-hosted Postgres setup is "hundreds/sec sustained, scale-out requires RabbitMQ or sharding configurations."
- The Postgres-native durability claim holds: Hatchet Lite is Postgres-only by default since v0.55.0 (maintainer-confirmed in https://github.com/hatchet-dev/hatchet/issues/1737), and queue/state mutations are transactionally persisted ([T1] guarantees page).
- **Maturity asymmetry is real:** Hatchet's durable-execution revamp merged 2026-03-16 (PR #2954); v0.101.27 (2026-08-17) still contains active durable-task work ("durable task performance improvements", "wire up split tx writes for durable events", "add load test for durable tasks" PR #4607), and the docs candidly describe durable tasks as "a fancy cache." §23's requirement — "jobs restartable after container restart" — is carried by the newest subsystem of the entire stack.
*Why it matters here:* §23 is a hard DoD item; betting the durable-job story on 5-month-old durable-execution code is a different risk than T1's "Temporal is mature." Direction can still stand (Postgres-native burst beats Temporal's ~50–200 starts/s Postgres ceiling), but the numbers and the maturity acceptance must be restated, and the Temporal fallback trigger conditions written down (e.g., "DAG deepens into multi-entity sagas requiring deterministic replay beyond current single-entity state machines").
**Citations:** T1: Hatchet guarantees/tradeoffs + benchmarking docs + issue #1737 + v0.101.27 release notes (URLs above, checked 2026-08-25); T2: Temporal community start-rate thread (from T2 record).

**3. Hatchet's audit-logs API is NOT available self-hosted — the "unverified" provisional resolves to "not available"; mitigation is mandatory, not optional.** Official docs (published 2026-08-21): **"Audit logs are available on Business plans and above. If you're on the open-source edition and need audit logs, contact us to learn more about upgrading."** ([T1] https://docs.hatchet.run/v1/security/audit-logs). The CHANGELOG confirms it shipped as a Hatchet Cloud Scale plan feature. RBAC is real self-hosted (RBAC v0 PR #3185; VIEWER role in v0.101.27) — that part of the claim holds. *Why it matters here:* T3 already compensates correctly ("job-run audit events are appended to our own semantic log so the §21 audit never depends on the engine's audit facility") — but that contingency must now be treated as the *committed design*, not a hedge; job-execution audit becomes a first-class API component. *Severity:* LOW (mitigation exists and is architecturally sound — arguably cleaner than depending on the engine), but record the status change.

**4. C's outbox closes write-durability but leaves four residues (C — dual-write).**
- **No read-side consistency contract:** A's token gate has no C counterpart. While the drainer lags, the triple store is stale relative to committed Postgres state, and no `stale_at`/wait mechanism is defined for semantic queries. The knowledge-service repo cited as evidence actually solved this with a **reader-side status filter** ("exclude in-flight content until terminal status — the half-picture problem," its architecture doc); refined C should adopt an equivalent (exclude assertions not yet drained, or expose drain lag in response envelopes).
- **Ordering unspecified:** overrides/supersedes must not be drained before the assertions they supersede. Requires per-entity ordering (single drainer per sequence key, or partition-keyed dispatch) — the pattern literature is explicit that parallel relays reorder without a partition key ([T2] sade.dev 2026-06-22; atlasofengineering.com).
- **Authority-of-record ambiguity:** with the assertion durable both as an outbox row in Postgres AND as the drained triple, which is the rebuild source when they disagree (drainer bug / ASK-guard skip / partial retraction)? The named-graph snapshot audit lives in the triple store; write-durability lives in Postgres. C needs an explicit divergence-reconciliation policy (§34 "inconsistent data across storage technologies" test exists precisely for this).
- **Operational burden is documented, not hypothetical:** the outbox literature is packed with failure modes that must become §33/§34 items — relay stall while writes continue, unbounded outbox growth, poison events blocking the relay, `SKIP LOCKED` contention under scale ("10M pending messages" and "relay DDoS'ing its own DB" in one Black-Friday report; 40% throughput regression from the extra outbox insert in one benchmark), and the note that "the most common mistake is to treat the outbox as a queue without operational ownership" ([T2] banandre.com 2025-11-19; atlasofengineering.com; sade.dev; arc42 quality model 2026-07-10). None of this kills C — it defines the drainer's real budget.
- **Evidence tier:** the knowledge-service repo (arshadansari27/knowledge-service) exists (verified 2026-08-25), MIT-licensed, ~700 tests, self-described as "a personal knowledge service" (8 stars) — a legitimate *pattern* reference (outbox same-tx, startup drainer, reader-side filter, Noisy-OR confidence) but T3-scale evidence, not "production-grade at this system's scope." The "direct small-scale working analog" claim is fair if labeled as such; it should not be carried into the DD as production proof.
**Citations:** T2: distributedrequest.com (2026-07-06) — exhaustive outbox mechanics; atlasofengineering.com/computer-engineering/transactional-outbox — failure-mode list; quality.arc42.org/approaches/transactional-outbox (2026-07-10) — relay = new stateful component, consumers must dedupe; sade.dev (2026-06-22); banandre.com (2025-11-19); T3: github.com/arshadansari27/knowledge-service (verify-tier: personal project).

**5. RDF-star adoption is right for today but the migration to RDF 1.2 triple terms is *semantic*, and the Jena fallback is experimental (C — semantics).** Verified (2026-08-25): Jena 6.1.0 (2026-05-11) genuinely ships RDF 1.2 support — `StatementTerm` Model API (triple terms, object-position only), `Model.createReifier`, RDF/XML 1.2, SPARQL 1.2 formats — but its own CHANGES.txt labels this **"In this experimental release"** with "The RDF 1.2 / SPARQL 1.2 specs aren't finished." (*Why it matters:* the fallback is real but experimental-stage; and since GraphDB production repositories are LMDB-backed while triple-term support targets MemoryStore first with **LMDB explicitly deferred** ([T1] Ideator's RDF4J #5327 citation; corroborated by T2 GraphDB 11.4 star docs still framing RDF 1.1 extension), the realistic migration is *when engines converge on REC*, not sooner). The Ideator's own wording ("truth/preference is a projection") already points at the clean resolution: **make C's triple store a replay-built projection over A's event log** — then C is fully honest (single write path, no drainer lag problem, no authority ambiguity), and the "asserting vs non-asserting" question becomes internal to the projection builder, which can be swapped when engines reach REC. ### Pattern 1: The Decomposition DAG as Hatchet Durable DAGs, with Semantic-Log Stage Artifacts (§6, §16, §23)
**Shape:**
- Model the §6 pipeline (INGEST → FORMAT ANALYSIS → BASIC SEGMENTATION → LOW-LEVEL EXTRACTION → STRUCTURAL ANALYSIS → ENTITY RESOLUTION → CROSS-SOURCE ALIGNMENT → SEMANTIC RECONCILIATION → KG) as a **Hatchet DAG workflow**. Each §6 stage is a **task node**; edges are explicit `parents` dependencies. Hatchet's declarative DAG executes independent tasks in parallel, passes parent outputs to children, and persists each task's status+result so a retry resumes at the failed node without re-running completed stages (docs.hatchet.run/dags — "DAGs in Hatchet are a form of durable execution… every time a task completes, Hatchet persists its status and result so the DAG can be retried without re-executing succeeded parts"). This is the §23 "late failure doesn't repeat early extraction" guarantee, engine-native.
- **Idempotency gates per stage:** every stage task carries an **idempotency key** = deterministic function of (source_id, stage, extracting-model-version, input-evidence-refs, stage-schema-version) (Hatchet idempotency: CEL expression against input; docs.hatchet.run/v1/idempotency; jobrunr/docs.hatchet-run "stable key invariant across retries"). Stage handlers append a `StageCompleted(source_id, stage, artifact_refs, version)` event to the semantic log **in the same Postgres transaction** as the projection of that stage's artifact rows, so stage completion is itself evidence-bearing (§2) and never double-committed.
- **Per-stage artifact records:** a `stage_artifact(artifact_id, source_id, stage, locator_prefix, blob_ref, produced_by, created_seq, run_id)` table recorded in the log transaction. Blobs never touch Postgres — they are written to OCFL via **ocfl-py** (see Pattern 7) and referenced by their content-address (sha512) in `blob_ref`. This is the "raw bytes flow to object storage, Postgres holds references only" rule from §22.
- **Lazy/streamed processing of large media:** stages consume their parent's *locator ranges*, not whole blobs. A 90-minute video/audio source is segmented (§6 → Pattern 2) into locator-bearing chunks in the SEGMENTATION stage; the low-level extraction stage fans out one task per chunk (Hatchet **batch tasks** accumulate per-chunk work and flush on max-size/interval — docs.hatchet.run/v1/batch-tasks), so no stage loads the entire media into memory. Extraction reads OCFL content via ranged/streaming reads (PyAV/ffmpeg demux by PTS, §2.4) rather than full-file decode.
- **Invalidation/rerun (§16):** an `Invalidate(source_id | segment | entity, scope, reason, caused_by)` log event triggers recompute of **only** dependent stage tasks (Dagster-declared asset lineage below); Hatchet reruns those nodes; successful upstream nodes are skipped via idempotency keys. Invalidation is always a log record — it never mutates history, satisfying §7/§15.
- **Division of labor (T4 concern 8 — RESOLVED):** **Dagster software-defined assets declare the projection/DAG + freshness metadata and dependency lineage only; Hatchet is the only runner; Dagster's auto-materialize/daemon schedulers are disabled in production.** One system computes rebuilds. Dagster runs nothing.
- **Temporal fallback trigger conditions (T4 concern 2 — RESOLVED):** written down now: switch from Hatchet to Temporal *if and only if* either (a) orchestration deepens into multi-entity sagas requiring **deterministic code replay** beyond single-entity stage state machines, or (b) human-in-the-loop §7 approval flows require durable **event/signal** waits coordinated across entities at a scale where Hatchet's checkpoint model (a "fancy cache," per its own docs) is insufficiently deterministic. Trigger is mechanical — both engines run the same stage functions behind the task interface.
- **Job-run audit is a committed component (T4 concern 3 — RESOLVED):** because Hatchet OSS has **no self-hosted audit-logs API** (docs.hatchet.run/v1/security/audit-logs: "Audit logs are available on Business plans and above"), the design **commits** that every stage start/retry/fail/complete appends a `JobRunAudit` record to the semantic log (same event stream as semantics). §21's audit therefore never depends on the engine's facility and is uniformly queryable.

**Production evidence:**
- T1 (Hatchet docs): declarative DAGs are durable by definition; status+result persisted per task — https://docs.hatchet.run/dags — proves the "resume without re-running completed stages" claim §23 needs.
- T2 (Hatchet announcement): idempotency keys + batch tasks shipped in OSS — https://hatchet.run/announcement/idempotency-keys-and-batch-tasks — proves dual primitive for stage-gating and fan-out.
- T1 (AWS Durable Execution SDK): idempotency keys generated *inside* a step are stable across replay; at-least-once + idempotent consumer = effectively-once — https://docs.aws.amazon.com/durable-execution/patterns/best-practices/idempotency/ — validates the "generate key inside the stage, never outside" rule.
- T1 (Temporal): activities at-least-once; activities must be idempotent; workflow-run + activity id forms a stable key — https://temporal.io/blog/idempotency-and-durable-execution — corroborates the durability contract both engines rely on.

**Maps to:** §6 (DAG stages), §16 (selective invalidation), §23 (durable restartable jobs), §22 (blob ownership), §2 (stage outputs evidence-bearing).

### Pattern 2: Segment Identity + the `source://` Locator System (§8–§9, §19, §28)
**Shape:**
- **Deterministic segment IDs:** a segment ID is `sha256(canonical-source-id + ":" + modality + ":" + deterministic-structural-path)` truncated to 128 bits, encoded URL-safe. It is *content-deterministic*: re-segmenting the same source yields the same IDs (required by §8 modal hierarchies with universal locators), and it never collides across re-uploads because `canonical-source-id` derives from the OCFL content hash of the source — never a user filename (§32).
- **`source://` locator grammar** (per T-series tech research §3.1, now made concrete): `source://<canonical_source_id>/<modality>/<segment_id>[?frag=...]`, where the fragment adopts the relevant standard selector so locators are *portable* and *source-native*:
  - text/book → `epubcfi(...)` (EPUB CFI 1.1 structural path+text-location assertion; EPUB 3.3 W3C Rec 2026-01-13).
  - image/page/comic → IIIF Image API 3.0 `xywh=` / `pct:` region.
  - audio/video → W3C Media Fragments `t=start,end` + optional `track=` / spatial `xywh=` (§8 time-based and region-based media).
  - subtitle track → Media-Fragments-compatible `t=` over the cue boundaries, framed by track identity (`track=`) so HI/SDH and multiple tracks are addressable independently (§27 — never flattened).
- **Segmentation tables structured per modality:** a shared `segment(segment_id, source_id, modality, parent_segment_id, locator_jsonb, ordering, evidence_hash)` table with a **modality-specific** `segment_blob_ref`/`locator_jsonb` payload. Modal segmentation hierarchies literalize §8 as a `parent_segment_id` self-join (e.g. video: scene → shot → frame-region → face/object crop; text: chapter → paragraph → sentence → token). The `locator_jsonb` stores the canonical structural path + the portable fragment; `evidence_hash` ties the segment to the exact OCFL bytes it was derived from (so a re-extraction that changes bytes visibly bumps evidence without breaking the locator's identity, §28 canonical structures retain realizations).
- **Locator resolution API (§19):** `GET /segments/{locator}` resolves any `source://` locator to: (a) the structured segment row, (b) the OCFL-resolved media range (a `Range`/`t=`-aware read of the underlying blob for a preview/thumbnail endpoint), and (c) every **evidence** and **semantic** record that anchors to that locator (both directions, kind-tagged per §20). Resolution never round-trips the full blade; it returns the object ref + ranged pointer. Source-native retrieval (#19) is this endpoint over OCFL content.
- **C challenger note (claim-graph projection):** if C's RDF-star graph becomes a projection, locators are the `subject`/`anchor` IRIs; a `source://` locator maps 1:1 to an RDF subject IRI (percent-encoded), so the projection builder and the source layer share identity without a second ID scheme.

**Production evidence:**
- T1 (specifications): EPUB CFI 1.1 and EPUB 3.3 (W3C Rec 2026-01-13) for text-location assertions against drift — https://w3c.github.io/epub-specs/epub33/epubcfi/ ; W3C Media Fragments URI 1.0 (Rec 2012) for `t=`/`xywh=` — https://www.w3.org/TR/media-frags/ ; IIIF Image API 3.0 for canonical spatial crops — https://iiif.io/api/image/3.0/ — all pre-validated in the tech-research report (carried).
- T2 (community): canonical URN/content-addressing is the standard way to make fragment locators stable across reprocessing; the tech research §3.1 recommends exactly the content-hash-derived `source://` scheme — carried from `/workspace/Universeity/artifacts/designs/process/universal-media-decomposer-technology-research.md` §3.1.
- T1 (OCFL): content-addressed sha512 manifest is the layout contract — https://ocfl.io/1.1/spec/ (carried).

**Maps to:** §8 (universal locators + modal hierarchies), §9 (stable source-native locators), §19 (source-native retrieval), §27 (independent subtitle tracks), §28 (canonical structures retain realizations).

### Pattern 3: State Management — Semantic-Log Schema, Current-State Materialization, and the Read-Your-Writes Token Contract (§2, §7, §10, §15, §21, §36)
**Shape:**
- **Event envelope (concrete):** `semantic_event(seq BIGSERIAL, event_type TEXT, event_version INT, tx_time TIMESTAMPTZ NOT NULL DEFAULT now(), valid_time TIMESTAMPTZ, authority ENUM('MACHINE','USER_OVERRIDE','CONSENSUS'), confidence DOUBLE PRECISION, generated_by JSONB, correlation_id UUID, causation_id UUID, payload JSONB, schema_url TEXT)`. Event types (all past-tense, versioned): `SourceIngested`, `FormatAnalyzed`, `SegmentCreated`, `StageCompleted`, `EntityMentioned`, `EntityResolved(MERGE/SPLIT/ALIAS)`, `Aligned`, `SemanticAsserted`, `ContradictionRecorded`, `OverrideApplied`, `Locked/Unlocked`, `Invalidated`, `CorrectionApplied`. `seq` is the global position used by projections and the read-your-writes token.
- **Schema versioning/upcasting (enforce §2, T2-critique A1):** payloads are **weak-schema JSONB** validated by a JSON Schema artifact at `schemas/events/{type}/v{n}.json`; upcasts are pure `(payload, version) -> payload` functions colocated with the schema; CI gate rejects renames/removals/type-changes without an upcaster (Overeem's 8/19 systems violate this and forfeit the complete audit trail; youngju/KloudVin make it an executable rule, not a footnote). **Corrections are events** (`CorrectionApplied`), never in-place edits (§15 precisely).
- **Current-state materialization (two tiers — T4 concern 1 RESOLVED with a clean consistency story):**
  - **Tier 0 — inline current-state table, same transaction as the event append:** a `current_state(entity_ref | segment_ref, authority_winner, supersedes_seq, valid_range, payload_jsonb)` row that is the direct, transactional result of applying each event that *changes winner semantics* (overrides, merges, alignments with USER_OVERRIDE/winner precedence). This follows the event-driven.io/Oskar Dudycz thumb rule — "for single-stream, simple projections, prefer inline projections" — and is cheap because the winner-resolution per entity is a small, local computation (not a graph/vector rebuild). **Guarantees:** the §7 hot path (override then immediate query) reads Tier 0 in the same DB, transactionally, so it *cannot* serve pre-override truth with zero async lag.
  - **Tier 1 — async projections (graph/vector/search/claim-graph), replay-built by single-writer builders** with checkpointing, idempotent `UPSERT` handlers, and **blue-green rebuild** (build new `schema_name` table in background, atomic pointer swap; Protean "treat projection rebuilds as a deployment strategy": test in staging, `events_skipped==0`, blue-green, backfill priority lane). Tier 1 is where all heavy read models live.
- **Read-your-writes token + stale_at (T4 concern 1 — the budget-exceeded decision):**
  - Every mutating API call returns `read_your_writes_token = committed seq`.
  - **History/provenance (§21)** reads always hit the log/Tier-0 directly → always consistent by construction; never token-gated.
  - **Tier-0 current-state reads** are never stale (transactional) → no token needed.
  - **Token-bearing Tier-1 reads** wait up to a hard cap = configured lag budget × 2 (default ≤1s). **If the projection has caught up within the cap, serve. If it has not** (a multi-minute scheduled invalidation-rebuild is in flight), the API returns **`503` + `Retry-After`** (retryable) rather than serving stale — because serving stale breaks the §7 "override then immediate query never returns pre-override truth" contract. Requests *without* a token are served with a documented freshness bound and a `stale_at` marker in the response envelope.
  - Rationale: fail-fast-on-timeout is the only option consistent with §7; the Tier-0 inline table keeps that failure path rare (only graph/vector-heavy current-state queries can hit it).
- **Typed core + extensible JSONB predicates (§10, §36):** controlled `predicates` dictionary table (grows without migration) + a typed core of high-value relationships (speaks, present_in, CORRESPONDS_TO, ADAPTATION_OF, CONTRADICTS, DERIVED_FROM, ALIAS_OF) as first-class columns/enums; everything else is `predicate TEXT REFERENCES predicates(predicate)` + `object_jsonb` + `confidence` on the assertion. This avoids both §36 extremes (rigid schema / untyped blob) and keeps the RDF-export path (Pattern 7 C-projection) mapping predicates to property IRIs losslessly.
- **Dual-write avoidance:** because authority is a single write path (the log), there is **no outbox** in Refined A — the outbox residue set (T4 concern 4: read-lag, ordering, authority ambiguity, poison ops) never arises. The C challenger inherits this only if it is kept a co-authority; the T4-recommended C-as-projection collapses those costs (see Cross-pattern notes).

**Production evidence:**

### Pattern 4: Entity Resolution + Alignment — Reversible via Log Records, Confidence-Bearing, Many-to-Many (§4, §5, §12, §14, §29)
**Shape:**
- **Canonical entity is a projection-time construct; mentions are the durable facts (§29):** the log stores `EntityMentioned(mention_id, canonical_hint, source_locator, extracted_vectros/features)`. Resolution produces **log records**, never destructive rewrites:
  - `EntityResolved(MERGE, primary_id, merged_ids[], evidence_refs, confidence)` — reversible by a later `EntityResolved(SPLIT, ...)` or `UndoEntityResolved`; the graph/current-state projection applies merges and can be rebuilt to unwind them. **Merge is literally reversible** because the log keeps every constituent mention forever.
  - `EntityResolved(ALIAS, entity_id, alias_string, script/transliteration, confidence)` for エミリア/Emilia/Emilia half-elven, etc. Alias is an assertion, not a rename.
  - **Unnamed/later-resolved identities** are `unknown_N` placeholders carrying candidate sets (§14), promoted to a canonical entity by a later log record linking them.
- **Candidate-set storage (§14):** structured JSONB on the assertion: `speaker_candidates[{embedding_cluster_id, speaker_07, confidence}]`, `face_candidates[{face_cluster_id, ...}]`, `text_candidates[{normalized_name, script, score}]`. Confidence is end-to-end and queryable with thresholds (§20). This is exactly the "candidate sets as structured JSON, graph queries accept confidence thresholds" prescription from tech research §3.4.
- **Scoring/blocking (the resolver):** **splink** (Fellegi-Sunter model, unsupervised EM, term-frequency adjustments, interpretable match weights, DuckDB backend) for text-alias/name/transliteration candidate scoring; blocking keys = normalized name, transliteration, soundex, face-cluster id, speaker-embedding cluster id, MinHash-LSH to bound comparisons — carried from tech research §3.3 (splink: MIT, moj-analytical-services).
- **Many-to-many alignment (§12):** correspondence asserted as typed, confidence-bearing log records linking segments across languages/adaptations — `Aligned(segment_a_ref, segment_b_ref, relation∈{CORRESPONDS_TO, ADAPTATION_OF, CONTRADICTS, DERIVED_FROM}, confidence, alignment_source)`. Never merge evidence. Sentence-level many-to-many (1-many/many-1/many-many blocks) via **Vecalign** (linear-time approx DP over multilingual embeddings); word/term-level via awesome-align/SimAlign; temporal alignment via DTW over timecodes (tech research §3.2). The relationship, not the join, is stored — so `CONTRADICTS` coexists truthfully (§11: three hair colors coexist) and `ADAPTATION_OF` preserves realization separation (§28).
- **Maps §11/§28:** canonical entity holds shared semantic intent + multiple realizations, never collapsed into one authoritative sentence; contradictions ride on the log's ⊆-with-authority model.

**Production evidence:**
- T2 (official splink docs): Fellegi-Sunter model, blocking rules, EM parameter estimation, term-frequency adjustments, thresholded match weights, clustering — https://moj-analytical-services.github.io/splink/index.html and github.com/moj-analytical-services/splink — proves the candidate-scoring primitive for §12/§14/§29.
- T1 (UK MoJ / gov.uk): splink in production for record linkage at the Ministry of Justice, tens of millions of records, used for entity resolution across admin datasets — https://dataingovernment.blog.gov.uk/2022/09/23/splink-fast-accurate-and-scalable-record-linkage/ — production provenance for the library.
- T1 (ACL, carried): Vecalign many-to-many sentence alignment (D19-1136) for §12 — carried from tech research §3.2.

**Maps to:** §4 (multilingual), §5 (adaptation/continuity boundaries as typed relationships, not merges), §12 (many-to-many alignment), §14 (confidence/uncertainty), §28 (multiple realizations), §29 (reversible resolution).

### Pattern 5: Error Handling — Idempotent Stage Retry, Partial-Failure Recovery, Poison-Event Handling, Sandboxed Parsers (§23, §32)
**Shape:**
- **Stage idempotency + durable resume:** every stage is a unit of work that either (a) commits its output + audit event atomically in one Postgres tx, or (b) is retried from scratch by Hatchet. Because a stage is a *single* unit (durable resume granularity is the stage, not sub-steps — per jobrunr.runStepOnce doctrine, "if a step does two things and the job dies between them, the whole step re-runs"), each stage is kept as one small, idempotent, DB-committing unit. Expensive external/model outputs are made idempotent via deterministic keys (Pattern 1). This is the **partial-failure recovery**: a crash after SEGMENTATION but before LOW-LEVEL EXTRACTION retries only extraction — earlier completed stages are skipped by their committed audit events + idempotency keys (§23 "successful early extraction not repeated").
- **Poison-event handling (projections):** projection handlers that repeatedly fail on one event must not wedge the stream. Adopt the outbox/queue lesson even though Refined A has no outbox: a per-projection **poison-event quarantine** — after N failed applications of `seq`, move the event to `projection_poison(projection, seq, event_type, error, attempts)` and *skip it* (recorded as a skipped-event metric, Protan/EventSourcingDB `events_skipped` is a warning that needs investigation), letting healthy events proceed; page on-call. Tier-0 inline currents are never subject to this (they're transactional).
- **Sandboxed parser containment (§32):** all untrusted media parsers (pandoc, ffmpeg/PyAV, OCR, whisper, diarization, subtitle parsers) run as bounded subprocesses under **nsjail** (namespaces, rlimits, cgroups, seccomp via Kafel, time/mem/CPU/fd/pid caps, read-only binds), with rlimits/timeouts at every layer, upload guards (size/archive-safe/path-traversal), and **never trusting filenames** (OCFL content-addressed keys) — carried from tech research §2.7. A parser crash/fault is contained to its sandbox; stage failure is a normal retryable/poison path, never a service crash.
- **Poison/error classification:** distinguish (a) transient (network, resource) → automatic Hatchet retry with backoff; (b) deterministic input problem (malformed but parses-fail) → quarantine + partial-failure record, upstream segments continue; (c) integration/bug → alert + human. Error taxonomy is part of the OpenAPI problem+json envelope (§24, RFC 7807).

**Production evidence:**
- T1 (AWS Durable Execution SDK): step execution semantics; at-least-once vs at-most-once per retry; make each step a single unit of work; idempotent writes — https://docs.aws.amazon.com/durable-execution/patterns/best-practices/idempotency/ — the partial-failure semantics.
- T2 (JobRunr): `runStepOnce` resume-after-failure granularity; step markers in the same DB as the job; keep each step a single unit of work; idempotency required for the in-flight step — https://www.jobrunr.io/en/guides/advanced/durable-executions/ — the durable-step granularity rule.
- T2 (outbox/poison literature): poison rows must go to a quarantine/DLQ after N attempts so one bad message never blocks the rest; `SKIP LOCKED` parallel workers; DLQ + alert — https://www.glukhov.org/app-architecture/integration-patterns/transactional-outbox-pattern-go/ and https://tiarebalbi.com/en/blog/the-transactional-outbox-is-not-a-queue — the poison-handling pattern adopted for projections.
- T1 (nsjail): namespaces/rlimits/cgroups/seccomp bounded subprocess sandboxing — https://github.com/google/nsjail (carried).

**Maps to:** §23 (durable restartable jobs / no repeated early work), §32 (sandboxing untrusted parsers), §24 (structured error envelope).

### Pattern 6: Testing Strategy — Synthetic Media Fixtures, Determinism Replay, Conformance (§34, §40)
**Shape:**
- **Synthetic media fixtures, generated not committed:** a `tests/fixtures/` package whose generators produce deterministic, tiny, codec-clean media via FFmpeg `lavfi` sources + synthesized audio (tones/ascending scales), committed references for golden compares — NOT large binaries in git. This is the podkit/fastrender/mediapipeline pattern: sub-second `lavfi` `sine=`/`testsrc2=`/`color=` clips pinned to a specific FFmpeg build (CI_FFMPEG_SHA check), so no third-party content and deterministic input.
  - **Required fixture matrix (§34/§40):** a book (e.g. tiny EPUB via ebooklib) **plus its translated/adapted books** (multilingual, script-different names); **comic/manga pages** (panel boxes, bubbles, vertical CJK text via PaddleOCR); **multi-speaker audio** (concatenated distinct synthetic speakers for ASR+diarization); **dialogue video** (scene boundaries via PySceneDetect over synthetic scenes); **multiple subtitle tracks** (SRT/WebVTT/ASS/TTML), **HI + SDH tracks** distinguished only by disposition (the Novus subtitle-fixture shape: language + forced + hearing_impaired + empty-track + swapped-language edge cases); **adaptation differences** (same story, different events/chapters — the §5 alignment + §11 contradiction fixture); **contradictions** (three "hair color" statements across sources); **missing/reordered events**.
- **Determinism test (§34; T2-critique A2 enforcement 3):** wipe each projection store (graph/vector/search/claim-graph), reset checkpoints to 0, replay the log over the fixture corpus, **diff checksums against the pre-wipe copy — must match exactly** (KloudVin's "projections are pure functions of the log — truncate, replay, diff"). Any non-projector write path → the diff fails → CI fails. This is the standing proof that §2's "rebuild by replay" holds and that single-writer-to-projections is enforced structurally.
- **Conformance tests (§34):** (a) **locator conformance** — generated locators parse to the same segment on re-segmentation; (b) **C/RDF conformance (if claim-graph projection adopted)** — assert the pinned triple-term/RDF-star semantics: embedded-triple presence ⇒ assertion, retraction removes it; fail loudly on engine drift (T3's §34 pin); (c) **merge/split reversibility** — merge entities, revert, assert original mentions restored and audit explains the change; (d) **ID stability** — re-ingest same source, assert same segment IDs.
- **E2E correction→invalidation→selective-rerun (DoD #30):** ingest several related heterogeneous sources → decompose → align → resolve → graph → answer with source refs → user corrects an entity → assert `Invalidated` event → only dependent stages rerun (assert unaffected asset IDs unchanged via checksum) → new answer reflects the correction → audit trail explains it (§7, §16, §21). Assert the Tier-0 override-then-immediate-query guarantee directly.
- **Property/rapid testing:** generate randomized plausible media/metadata and property-check invariants (locator determinism, merge-reversibility, no out-of-range timecodes) — Hypothesis for Python.

**Production evidence:**
- T2 (podkit test-fixtures): deterministic synthetic audio+video fixture sets, generated on demand, gitignored, codec matrix — https://github.com/jvgomg/podkit/tree/main/test-packages/test-fixtures — the "generate, don't commit binaries" fixture architecture.
- T2 (fastrender): lavfi-built H.264/AAC/VP9/Opus fixtures with `-bitexact` for determinism, CC0/third-party-free — https://github.com/wilsonzlin/fastrender/blob/main/tests/fixtures/media/README.md — the exact deterministic-encode technique.
- T2 (Media Pipeline): layered CI (unit→integration→golden PSMR/SSIM/LUFS contracts), pinned FFmpeg SHA, deterministic-over-exact, golden-file maintenance as deliberate review — https://www.mediapipeline.org/pipeline-automation-batch-processing/ci-cd-and-testing-for-media-pipelines/ — the media-CI playbook.
- T2 (Novus subtitle examples): multi-track / forced / SDH-by-disposition / swapped-language / empty-track fixtures — https://examples.novusstreamsolutions.com/for/subtitle-testing — the §27 fixture shape.
- T2 (KloudVin): rebuildability diff test (truncate→replay→exact match) — https://kloudvin.com/article/event-sourcing-aggregate-design-snapshots-projections/ — the determinism-test authority.

**Maps to:** §34 (serious tests incl. provenance-loss / irreversible-merge / invalidation-error probes), §40 (definition of done), §16 (selective-rerun E2E), §27 (subtitle tracks).

### Cross-pattern integration notes
- **Single write path collapses T4 concern 4's outbox residue set.** Because Refined A has exactly one authoritative write path (the log; Tier-0 inline current-state is part of that same transaction), there is never a read-side lag contract, an ordering hazard, an authority-of-record ambiguity, or a poison-relay DDoS for semantics. Those costs existed only for C-as-co-authority. Patterns 3's Tier-0/Tier-1 split gives C's "co-existence of three hair colors" (§11) and Granola precedence (§7) a correct, low-lag home *without* an outbox.
- **The read-your-writes budget decision (T4 concern 1) is closed** by the Tier-0 inline table + fail-fast 503 policy — the §7 override-then-immediate-query guarantee holds transactionally; graph/vector-heavy current-state reads either meet the lag budget or fail retryable rather than lie.
- **C as claim-graph projection (T4 concerns 4–5, and the T4-recommended fork) is fully implementable on these patterns:** the single-writer builder that reconstructs the RDF-star graph from log events is just another Tier-1 projection (Pattern 3), internalizing BOTH (a) the reader-side status/lag contract (the projection lags → the §20/§22 response envelope carries `stale_at` exactly like any Tier-1 read) and (b) the "asserting vs non-asserting" question (it becomes internal to the projection builder, swapable when engines reach RDF 1.2 REC, per T4 concern 5). C inherits every projection guarantee for free; it no longer needs its own drainer, outbox, ordering, or divergence policy. The GraphDB-EE-vs-Jena tradeoff (Pattern 7) becomes a pure projection-engine choice, authority-neutral.
- **The Counter-Improver should attack:** (1) the Tier-0 inline current-state table — does same-transaction materialization reintroduce write-path coupling/deadlock at burst scale, and is a per-entity winner-resolution actually cheap enough? (2) the fail-fast 503 policy — is 503 the right §24 semantics, or should a retryable 409/425 be a distinct code; does it interact badly with long invalidation windows? (3) Hatchet's durable-DAG resume granularity — is "stage = single idempotent unit" actually achievable for the lazy/streamed extraction fan-out without re-downloading OCFL content on every retry? (4) the §29 merge/split reversal — does `EntityResolved(SPLIT)` fully restore mention-evidence links, or do alignments pointing at a merged canonical entity need explicit rebinding records? (5) fixture determinism — are lavfi-generated media deterministic enough across the pinned FFmpeg build for the wipe→replay→checksum test to be stable in CI?

**Status:** DONE — 7 implementation patterns proposed with tiered production evidence and library validations; T4 mandated resolutions 1, 2, 3, 8 implemented inline; C-as-projection reading operationalized. Appended to `artifacts/designs/process/universal-media-decomposer-adversarial-log.md`.

### Risks: Pattern 1 — Decomposition DAG as Hatchet durable DAGs (semantic-log stage artifacts)

- **R1.1 — Hatchet idempotency is BETA with confirmed exactly-once bugs (⚠️ Improver surface 3, deeper).** Mechanism: idempotency keys via CEL expression + TTL sliding-window or status-based dedup shipped merged 2026-05-29 (PR #4045); docs state "Idempotency is currently in beta and may be subject to change." Confirmed bug #4129 (open, by security auditor m-be290108): scheduled-workflow trigger is a non-atomic 3-step (CreateIdempotencyKey → mq.SendMessage → DeleteScheduledWorkflow) with wall-clock-anchored TTL (TriggerAt+30s) — lost/delayed/duplicate executions, exactly-once violated. Fix PR #4454 (merged 2026-07-17) addressed the concurrent duplicate-key SQLSTATE 23505/SKIP LOCKED case only. Issue #3674 (open): child workflows keyed on childIndex — collision-prone; breaking change planned. Trigger: our design gating invalidation re-runs on idempotency keys; even though we are event-triggered (not scheduled), the same non-atomic key+message+TTL mechanism applies to any keyed invocation. Blast radius: duplicate MERGE/EntityResolved side-effects or silently dropped stage runs. Mitigation: treat engine dedup as best-effort — the semantic log must carry `UNIQUE (idempotency_key)` on stage-completion events and stage handlers must dedup before side effects (handler-level dedup is the authority). Severity: HIGH. Citations: [Tier 1] hatchet-dev/hatchet#4045, #4129, #4454, #3674 (github.com/hatchet-dev/hatchet, checked 2026-08-25).

- **R1.2 — DAG retry machinery is actively buggy across our exact DAG shapes.** Mechanism: recent fix trail — #3860 "Occasional empty payloads on DAG task retries" (fixed 2026-05-11); #1507 "input is nil" when a multi-step DAG with CEL concurrency plus parent-failure plus child-cancel is replayed; #1620 retry+cancel race (2025-04); #3243 "failure after cancellation would trigger a retry"; #4372 skip-entry ordering non-determinism in durable child spawn-index collision (fixed 2026-07). Trigger: our pattern = parent extraction stage fans out to child chunk tasks, task retries, and invalidation cancels children — a dead match for #1507/#3243/#1620 shapes. Blast radius: re-running extraction on already-completed chunks (violating §23 "late failure must not repeat early extraction") or "input is nil" crashes on replay. Mitigation: pin a Hatchet version ≥ the merged fixes; add CI regression tests for exactly these DAG shapes (cancel-parent-then-retry, child-cancel-then-parent-fail); keep the Temporal fallback triggers documented and tested. Severity: MEDIUM-HIGH. Citations: [Tier 1] hatchet-dev/hatchet#3860, #1507, #1620, #3243, #4372 (checked 2026-08-25).

- **R1.3 — "Stage = single idempotent unit" is engine-level, not cost-level (⚠️ Improver surface 3).** Mechanism: Hatchet durable resume persists per-task results so a DAG retry skips succeeded tasks, but a retried *task body* re-runs completely — including re-reading OCFL content. For lazy/streamed chunk fan-out on S3-backed OCFL, "no repeated early extraction" (§23) holds at the engine level but re-incurrs network reads on every retry. Trigger: large fixtured episode with 36k+ chunk tasks under partial failure. Blast radius: retry storms cost bandwidth + re-derivation, silently violating the §23 cost promise. Mitigation: stage handlers must first look up committed artifact by idempotency key and skip re-derivation; derived per-chunk artifacts cached in OCFL. This must be written down as a handler contract, not assumed. Severity: MEDIUM. Citations: [Tier 3] Hatchet DAGs docs — durable tasks "should be idempotent" guidance; jobrunr ruby docs on step-level atomicity (checked 2026-08-25).

- **R1.4 — JobRunAudit events in the semantic log inflate seq and replay cost.** Mechanism: every stage start/retry/fail/complete × audit record; a 36k-chunk fan-out batch = ~150k audit events appended in the same log that projections replay. Tier-1 replay builders must skip or partition by event_type or catch-up time grows with ops volume, not work volume; the wipe→replay→checksum test (Pattern 6) will checksum ops noise unless audit events are excluded from fixtures. Trigger: all batch runs at scale. Blast radius: token-wait 503s during ingestion bursts for reads waiting on Tier-1 catch-up (compounds P3-R3). Mitigation: partition projections by event_type, exclude audit from the determinism fixture, checkpoint position advances past skipped events. Severity: MEDIUM. Citations: design-internal (the log IS the authority; event volume arithmetic). [Tier 6] — analysis, not a library defect; labeled as such.

- **R1.5 — "Hundreds/sec" honest baseline → batch windows.** Trigger: T4-established baseline (hundreds/sec Postgres-only; 10k/s needs tuned RDS+RabbitMQ). A 36k-task fan-out = minutes of ingestion at the honest baseline — fine for batch, but the scale-out path (RabbitMQ/sharding) must be written down as an operational commitment, not assumed. Severity: LOW. Citations: [Tier 3] Hatchet docs guarantees-and-tradeoffs (verified T4 2026-08-13).

### Risks: Pattern 2 — Segment identity + source:// locator system

- **R2.1 — Content-hash source IDs break locator stability across byte-different re-uploads (⚠️ Improver surface, deeper).** Mechanism: canonical-source-id is the OCFL content hash; segment_id = sha256(canonical-source-id + modality + structural path). A byte-different re-upload of "the same" work (different release/encode) yields a brand-new source id and *every* segment id + locator under it. Downstream user overrides, EntityResolved alignments, Aligned records, and claim evidence refs anchored to old locators silently dangle. The §9 stabilty guarantee ("stable across reprocessing") in fact holds only across reprocessing of *identical bytes*. Trigger: our §8-9 multilingual corpus — users re-upload the same episode from a different release. Blast radius: user-edit store (§22) and alignment layer decay; DoD #34 "broken locators" class. Mitigation: a work-level grouping record (`SourceAliased` or WORK membership event in the log) plus an explicit override-transfer policy at ingest; dedup only byte-identical uploads (OCFL content addressing). This is a *design decision the Improver must make*, not a library bug. Severity: MEDIUM (design gap). Citations: [Tier 3] OCFL 1.1 content-addressing semantics; design-internal §8-9. [Tier 6] framing — decision, not defect.

- **R2.2 — Locator stability depends on decoder/renderer version churn, which the design does not version.** Mechanism: "deterministic structural path" is only deterministic if the segmenter/decoder/renderer is pinned AND its output is deterministic. PDF page rasterization changes with Poppler/MuPDF versions → OCR box coordinates (IIIF xywh in page-pixel space) change → locators change. Media PTS-derived `t=` locators shift across ffmpeg demuxer changes (VFR, edit lists). EPUB CFI stability is explicitly *bounded*: the spec itself mandates "the CFI MUST be considered an invalid reference" when assertions fail and a corrected CFI cannot be derived — and (W3C EPUB-WG minutes, Ivan Herman) "if I add a new <p> in the middle, all the CFIs pointing to a later paragraph will be wrong." Trigger: any extractor version bump across the corpus → mass silent locator drift. Blast radius: all evidence anchors (§2), overrides, and alignment links drift unless re-validated. Mitigation: locator `v` component carrying the segmenter/decoder/renderer version that produced the structural path; generated_by must record the media-decoder version, not merely the model version; a locator-version bump triggers a §16 selective invalidation pass. Severity: HIGH. Citations: [Tier 3] W3C EPUB CFI 1.1 — Intended Target Location Correction + invalid-reference rule (w3c.github.io/epub-specs/epub33/epubcfi/, checked 2026-08-25); [Tier 5] W3C EPUB-WG locators meeting minutes 2021 (w3.org/publishing/groups/epub-wg/Meetings/Minutes/2021-04-21-epub-locators).

- **R2.3 — pysubs2 silently ignores WebVTT `X-TIMESTAMP-MAP` — subtitle locators offset.** Mechanism: VTT tracks from HLS/broadcast carry `X-TIMESTAMP-MAP=LOCAL:...,MPEGTS:...` (an MPEG-TS offset, tick = 1/90000 s). pysubs2 issue #34 is open and unhandled; times are read verbatim. A subtitle event locator is wrong by the MPEGTS delta; alignment to audio (`subtitle_cue ↔ audio t=`) breaks silently. Trigger: our §27 subtitle-track pipeline ingesting HLS-originated VTT (very common in the corpus). Blast radius: wrong evidence locators in subtitle-derived events and alignments. Mitigation: pre-process X-TIMESTAMP-MAP (apply offset) before pysubs2 or detect-and-flag; add to §34 subtitle fixtures. Severity: MEDIUM. Citations: [Tier 1] tkarabela/pysubs2#34 (open, includes SubtitleEdit reference implementation), checked 2026-08-25.

- **R2.4 — pysubs2 is not a broadcast-subtitle parser by its own stated goal.** Mechanism: docs — "Support for production/broadcast subtitle formats … is not really a goal of the library"; ASS override tags round-trip lossy; encoding autodetection absent (UTF-8 default; `errors="surrogateescape"` needed for mixed encodings). Trigger: multi-language subtitle tracks with non-UTF-8 encodings and typesetting. Blast radius: mojibake or dropped formatting in subtitle-derived text evidence. Mitigation: charset-normalizer probe + surrogateescape passthrough; keep raw subtitle bytes in OCFL as the evidence source of truth, never only the parsed form. Severity: MEDIUM. Citations: [Tier 3] pysubs2 docs (readthedocs 1.9.0, checked 2026-08-25).

### Risks: Pattern 3 — State management (semantic log + two-tier materialization)

- **R3.1 — Tier-0 same-tx winner-resolution can become a hot-row/long-hold write path (⚠️ Improver surface 1).** Mechanism: every semantic event + current_state upsert in one tx; per-entity winner-resolution over mentions (override/merge precedence) must be bounded. For a merged entity with 100k mentions (Doomen-class stream), a full-scan resolution inside the tx both serializes writers on the entity row and holds locks long. Trigger: merge churn on popular characters (§29) under burst. Blast radius: §7 hot-path override latency spikes; deadlock-retry storms. Mitigation: keep resolution to an indexed last-write-wins per (entity, predicate) — never full-stream — with an explicit bound and a burst test in Pattern 6. Summation is *cheap if bounded*; the Improver must state the bound. Severity: MEDIUM (mitigable; requires measurement). Citations: [Tier 5] Doomen/ES patterns on long event streams; [Tier 3] PostgreSQL row-level locking docs. Engineering-analysis label where no defect citation exists.

- **R3.2 — Tier-0 vs Tier-1 divergence is a two-implementation correctness gap.** Mechanism: Tier-0 winner logic lives in the write path; Tier-1 builders reimplement precedence during replay. The §34 wipe→replay→checksum determinism test covers Tier-1 only. If the two drift, the §7 hot path (Tier-0) contradicts the §17 graph/QA view (Tier-1) — exactly the §40 DoD #34 "inconsistent data across storage technologies" probe. Trigger: any future change to precedence/override semantics (a fix in one path, not the other). Blast radius: silent authority divergence on the two reading surfaces the design *guarantees* consistent (§7/§20 envelopes). Mitigation: implement Tier-0 winner logic as *the same function* invoked by Tier-1 builders; extend the determinism test to rebuild Tier-0 as well (wipe → replay both → diff). Severity: HIGH. Citations: [Tier 2] the dual-write divergence postmortem literature already adopted in T2 (Nat Pryce, Verstaendig ASTRA 2021); design-internal. The fix is cheap; leaving it implicit is the risk.

- **R3.3 — Fail-fast 503 × long invalidation windows × retry storms (⚠️ Improver surface 2).** Mechanism: during a multi-minute invalidation rebuild, all token-bearing Tier-1 reads burn their wait budget and 503; naive clients retry immediately → request amplification that competes with the rebuild → longer rebuild (positive feedback). Server-side token waiting (polling projection lag) also occupies worker slots/connections. Trigger: exactly our §16 selective-invalidation workload (correction → cascade). Blast radius: cascading 503s + pool exhaustion during the exact window users care about most (post-correction reads). Mitigation: Retry-After honored + jitter; async bounded-concurrency waiters; consider distinguishing "rebuild in progress" (409/425-style, long-lived) from "transient lag" (503, Retry-After short) in §24 semantics — a decision for the Improver. Severity: MEDIUM. Citations: [Tier 3] §24/§20 contract design-internal; general retry-storm guidance (AWS Builder's Library retry patterns) for amplification math. Engineering-analysis.

- **R3.4 — HNSW index maintenance penalizes UPDATEs on co-tenanted tables (100×).** Mechanism: pgvector #875 — UPDATEs on non-vector columns of a table bearing an HNSW index: 6s vs 58ms for 10k rows, 3.7M vs 59k buffer hits; maintainer confirms "expected behavior" (the vector index marks entries for repair on *any* row write) and recommends a one-to-one split table. HNSW dead-tuple recall loss (#244, mitigated by iterative index scans in 0.8.0) and extremely slow HNSW vacuums (#450: 10h for 31GB) and tombstoned-node bloat (multigrid/paradedb writeups; 30% free_percent rebuild threshold). Trigger: our design bumps `evidence_hash` on segment rows on re-extraction, and supersede semantics may UPDATE embeddings in place. If an HNSW index shares a table with churned metadata (co-tenancy), every evidence_hash bump pays HNSW maintenance. Blast radius: silent 100× write slowdown; recall degradation over time without any error. Mitigation: embeddings on a *separate* table (1:1 btree FK) from churned metadata; append-only embedding rows per version (supersede = new row, never in-place UPDATE); rely on 0.8.x iterative scans; schedule REINDEX INDEX CONCURRENTLY + per-table autovacuum (scale_factor 0.01–0.05, cost_limit 2000+). Severity: MEDIUM-HIGH (silent-degradation class). Citations: [Tier 1] pgvector/pgvector#875, #244, #450 (checked 2026-08-25); [Tier 3] index-management.org HNSW bloat/autovacuum guidance (2026-07-17); multigrid.ai delete-from-vector-index (2026-08-07).

- **R3.5 — Blue-green schema swap under pooled connections can serve the dropping schema.** Mechanism: pgbouncer transaction pooling or SQLAlchemy-pooled sessions may pin a transaction/session whose search_path references the old schema name after `ALTER SCHEMA ... RENAME`. Reads then hit the dropped schema (stale or errors). Trigger: Tier-1 projection swap (the design's blue-green schema-name swap). Blast radius: brief stale-read window during swap — the exact §20 envelope guarantee is at stake. Mitigation: drop delay (no-drop grace period), explicit per-connection search_path, and a swap test in Pattern 6. Severity: LOW (operational, testable). Citations: [Tier 3] PostgreSQL schema search_path docs; pgbouncer pooling docs. Engineering-analysis.

- **R3.6 — Candidate-set JSONB threshold queries are not B-tree indexable.** Mechanism: confidence-threshold predicates over JSONB candidate-set arrays (Pattern 4's "graph queries accept confidence thresholds") cannot use regular btree; GIN path expressions re-scan. This is a *speculative performance note* (no confirmed regression found), not a defect. Severity: LOW. Cited honestly as analysis.

### Risks: Pattern 4 — Entity resolution + alignment (splink / Vecalign)

- **R4.1 — splink + DuckDB backend version regression makes blocking 15× slower or OOM (⚠️ Improver's flagged splink scaling, now concrete).** Mechanism: splink #2918 (2026-02): with DuckDB 1.4.x/1.5.x, two-dataset-link blocking collapses wide-CTE materialization → 2s→30+s same query, spilling to `.tmp`; uk_address_matcher#219: DuckDB 1.4.4 "unusable (out of memory error)" on 60M rows; DuckDB #21302: 1.5.x UNION ALL min() regression breaks query optimization; splink #3023 optimizer pushdown. Splink computes *all* buckets in parallel — one 4k-record low-cardinality bucket = ~8M comparisons simultaneously (discussion #3000: DOB blocking on 2M-10M records → 90GB disk-cache memory errors). Maintainers: 50+ blocking rules "cause performance issues" with SQL optimization. Trigger: our blocking keys include *low-cardinality* keys (speaker_07 raw label, face_cluster_id) + a multi-key rule set (normalized name, transliteration, soundex, face-cluster, speaker-embedding-cluster, MinHash-LSH) — the worst case. Blast radius: resolution stage OOM/hang during ingestion; DuckDB temp-disk exhaustion on shared worker storage. Mitigation: pin a splink-compatible DuckDB (1.3.x worked) or the equivalent splink release; keep blocking-key cardinality high (speaker *embedding cluster* id, not raw label); chunked prediction (splink v5 `predict_chunk`/`compute_blocked_pairs_for_predict_chunk`); run resolution inside a memory-capped sandbox boundary and treat it as a bounded batch stage. Severity: HIGH. Citations: [Tier 1] moj-analytical-services/splink#2918, #3000; moj-analytical-services/uk_address_matcher#219; duckdb/duckdb#21302; splink#3023 (checked 2026-08-25).

- **R4.2 — splink training-phase randomness breaks cross-run reproducibility.** Mechanism: splink's u-estimation (`estimate_u_using_random_sampling`) samples randomly; EM parameter estimates vary run-to-run → link probabilities and threshold-crossing decisions drift → different EntityResolved events on re-ingestion. Fine for replay (outcomes are in the log), but breaks §34 ID/conformance stability and cross-environment reproducibility (CPU vs GPU, seeds). Also splink is a batch tool; per-source incremental linkage needs a *persisted trained model* (train once, predict-only incrementally) — the design does not state training cadence. Severity: MEDIUM. Mitigations: train-phase checkpointing + fixed seed + predict-only increments. Citations: [Tier 3] splink docs (model estimation/sampling); the design's own reproducibility goal §40. Partly engineering-analysis — labeled.

- **R4.3 — Vecalign's monotonicity/contiguity assumptions fail for adaptation and non-parallel media (⚠️ Improver's flagged assumption, now peer-reviewed).** Mechanism: Vecalign (ACL D19-1136) prunes the DTW matrix with FastDTW-style coarse-to-fine on a ~10-sentence window assuming monotone, contiguous parallel text. Documented failures: Craig & Christodoulopoulos 2023 — non-monotonic/discontiguous translations and paratext (footnotes, alternate translations) violate "severe contiguity and monotonicity assumptions"; RASLAN 2021 (Hobbit/Alice literary eval) — first 10 alignments all wrong when book beginnings differ, blanks mishandled, cultural adaptations (rhymes) misaligned; Nature Sci Rep 2023 — quality degrades as source/target length difference grows (align smaller chunks); Neuralign EACL 2024 — Vecalign inferior on 1-to-0/0-to-1 and hard many-to-many; LaBSE substitution lowers F1 (LASER-only .emb format). Trigger: §12 alignment includes novel↔anime adaptation (reorders, omits, adds — §5) and subtitle-cue↔paragraph granularity mismatch — precisely the non-parallel case. Blast radius: wrong Aligned records carrying plausible confidence → corrupts §14 semantics, KG. Mitigation: scope Vecalign to genuinely parallel text pairs (novel ↔ translation) at sentence granularity; use DTW/timecode + embedding-retrieval + LLM reconciliation for adaptation/subtitle paths (already listed); Aligned records must carry alignment_source + a "parallelity assumption" field so consumers can discount. Severity: HIGH. Citations: [Tier 1/2] ACL D19-1136 (Venugopal 2019); Craig & Christodoulopoulos 2023 (khoury.northeastern.edu, peer process); RASLAN 2021 2nd-Workshop paper; Taylor et al., Scientific Reports 2023 (Nature); Neuralign EACL 2024 (checked 2026-08-25).

- **R4.4 — `EntityResolved(SPLIT)` must rebind downstream edges, not just mentions (⚠️ Improver surface 4).** Mechanism: the pattern defines MERGE/SPLIT/ALIAS as reversible log records with mention reassignment, but does not specify rebinding of *records that reference the canonical entity*: Aligned (segment_a/b), candidate-set membership, user overrides, claim evidence refs. After SPLIT, an Aligned edge pointing at the merged canonical entity is ambiguous (which constituent?) and remains unless explicitly rebound. Trigger: our §15/§29 flow (merge identities, later split on user correction). Blast radius: silent semantic corruption exactly what §34 probe #31 (irreversible merges) is designed to catch; a SPLIT must be either total (specify every edge's new target) or forbidden until the merge-time mapping is replayable. Mitigation: log merge-time mention→entity mapping; SPLIT carries explicit target assignment and a rebind cascade record; §34 test: merge→split restores all mentions AND all Aligned/override/candidate-set refs. Severity: HIGH (correctness gap as written). Citations: design-internal (§15, §16, §29); the EACL/Neuralign literature above shows downstream consumers treat Aligned edges as evidence — dangling edges poisoned.

### Risks: Pattern 5 — Error handling + sandboxing

- **R5.1 — nsjail-in-Docker deployment gap: sandbox needs privileges the worker container won't have (⚠️ Improver's sandbox design).** Mechanism: nsjail creates namespaces/cgroups; inside a Docker container the default seccomp profile + container namespacing blocks mount/namespace/cgroup operations unless the container runs `--privileged` (or `--cap-add=SYS_ADMIN --security-opt seccomp=unconfined --cgroupns=host`). Even then, PR #219 documents that with `--cgroupns=host` nsjail's cgroup limits land *outside* Docker's cgroup — Docker's own memory limit is not applied to the sandboxed child, and nsjail's limit is what actually governs (a defense-in-depth hole). Trigger: our §32/§38 architecture runs workers as containers that must launch nsjail sandboxes. Blast radius: either a privileged worker container (large container-level attack surface, defeats defense-in-depth) or a degraded sandbox with no working cgroup limits (unbounded memory). Mitigation: dedicated sandbox-runner container started privileged + seccomp=unconfined + cgroupns=host, treating the container itself as the outer boundary and nsjail as inner; OR bubblewrap (unprivileged user namespaces) for baseline isolation with cgroups as docs-only; the Improver must pick and document the security posture explicitly. Severity: HIGH. Citations: [Tier 1] google/nsjail PR #219 (cgroupv2/Docker note), issue #196; [Tier 4] nsjail google-group thread "Nsjail in docker" (checked 2026-08-25).

- **R5.2 — Strict Kafel seccomp allowlists break parser libraries in surprising ways.** Mechanism: nsjail seccomp violations SIGSYS the child; #118 documents a hang-not-kill when a policy omits `madvise` (imagemagick); #131: an execve-block policy also breaks nsjail's own execve; #159: ELF32-under-ELF64 policies unsupported. Our parser set (PaddleOCR/PyTorch/OpenCV thread+BLAS syscalls, ffmpeg, Python interpreter) is a moving target — a strict allowlist will break on any library upgrade; a loose one defeats the purpose. Trigger: any build/UV upgrade of a parser library. Blast radius: sandboxed stage deadlocks or spurious SIGSYS failures; if caught at runtime → non-obvious poison-class errors. Mitigation: per-parser policy files + a parser×policy CI test (each parser runs under its sandbox in Pattern 6's matrix); strace-derived allowlists; budget for allowlist maintenance on every parser bump. Severity: MEDIUM. Citations: [Tier 1] google/nsjail#118, #131, #159 (checked 2026-08-25).

- **R5.3 — PyAV runs FFmpeg in-process: July-2026 FFmpeg CVEs include RCE; PyAV must be inside the sandbox, spelled out.** Mechanism: current FFmpeg CVEs (fixed in 8.1.2+ commits): CVE-2026-64830 — VobSub subtitle demuxer heap buffer overflow via crafted .sub/.idx → arbitrary code execution; CVE-2026-66037 — IAMF demuxer 17-byte → multi-GB allocation during probe (~126M bytes per input byte); CVE-2026-64834 — RTP/ASF demuxer infinite loop DoS; CVE-2026-65704 — TY demuxer/Shorten decoder OOB write. PyAV links these in-process; a crafted media file = RCE in the worker process if PyAV runs there. Trigger: our §27 subtitle/§28 audio demuxing (VobSub is *directly* in our subtitle-track pipeline) — and the corpus is adversarial (§34). Blast radius: container/pod compromise (partial, if sandboxed — full if not). Mitigation: pin FFmpeg/PyAV ≥ fixed commits (with a CVE-watch process because this stream is steady), AND make explicit in the design that PyAV demux/decode runs inside the nsjailized subprocess, never in the API/worker body. Severity: HIGH (security). Citations: [Tier 1/2] FFmpeg security advisories July 2026 (CVE-2026-66037, CVE-2026-64830, CVE-2026-64834, CVE-2026-65704; ffmpeg.org/security.html, checked 2026-08-25); [Tier 3] PyAV docs (in-process ffmpeg bindings).

- **R5.4 — Whisper hallucination carries HIGH confidence — a §14 confidence-semantics leak.** Mechanism: faster-whisper #506 — repetition hallucinations output with "no easy way to find and react … confidence of the model in those situations is high"; #1249 — pure-music audio yields hallucinated speech segments even with VAD; #843 — Silero-VAD meta-hallucination (fixed by silero-vad v5 upstream, faster-whisper PR #884); #477 — faster-whisper's bundled VAD defaults differ from silero-vad (speech_pad_ms 400 vs 30; min_silence 2000 vs 100); #1312 — VAD threshold tradeoff (loud speech skipped vs hallucinated text in silence). Trigger: our anime corpus is music-heavy; §14 records confidence and generated_by for every claim. If ASR confidence is stored as evidence confidence, hallucinated text becomes *high-confidence semantic evidence*. Blast radius: corrupts §14/§17 KG edges and any downstream trust pipeline. Mitigation: pipeline-stage separation (VAD+language pin+hallucination filters: segment no-speech prob/compression-ratio/avg-logprob, whisperX-style); rule — VAD-no-speech ⇒ music/SFX segment, not ASR; re-label ASR confidence as *transcription* confidence, never semantic truth; keep hallucination filters in §34 adversarial probes. Severity: HIGH. Citations: [Tier 1] SysCV/faster-whisper#506, #843, #1249, #1312, #477, PR#884 (checked 2026-08-25); [Tier 2] WhisperX arXiv:2303.00747 (VAD Cut&Merge reduces hallucination/repetition).

- **R5.5 — Python tarfile/zip extraction CVEs — extraction is NOT a security boundary.** Mechanism: CVE-2025-4517 (CVSS 9.4, "arbitrary writes via realpath overflow", `filter="data"` bypass, fixed 3.10.18/3.11.13/3.12.11/3.13.4/3.14.0b3); CVE-2025-4330 (filter ignored, symlinks escape); CVE-2024-55587 (python-libarchive zip traversal). Python ≥3.14 silently flips `filter=` default to "data" — automatic behavior change that still had a bypass. Trigger: EPUB/CBZ/tar upload extraction in our §32 "safe archive extraction". Blast radius: file write outside the extraction dir (already the known OCFL-workflow breakout the Improver flagged). Mitigation: pin Python ≥ fixed versions; treat extraction as inside-sandbox-only (it is not the boundary — the sandbox is); never extract on the host path; add traversal tests to §34 probes. Severity: MEDIUM-HIGH. Citations: [Tier 1] NVD CVE-2025-4517 / CVE-2025-4330 / CVE-2024-55587 (checked 2026-08-25).

- **R5.6 — Poison-event skip can silently drop USER_OVERRIDE events from a projection.** Mechanism: per-projection quarantine + skip + events_skipped metric protects availability, but skipping a poison USER_OVERRIDE event means §7 semantics (override must be immediately visible) are silently violated in that projection. Trigger: a malformed (but authored) override event or validator bug. Blast radius: the graph/vector projection "forgets" an override without any error surfaced to the reader (only a metric). Mitigation: skip only for non-authoritative event types; for override/merge events, quarantine-and-pause the projection (fail loud) rather than skip, or serve a 503 with the quarantine reason; every skip increments a surfaced `stale_at`/divergence field. Severity: MEDIUM. Citations: design-internal (§7 guarantee, §17 envelope); [Tier 6] analysis.

### Risks: Pattern 6 — Testing (GENERATED fixtures, determinism, conformance)

- **R6.1 — lavfi determinism is build-scoped, and model-stage goldens will flake (⚠️ Improver surface 5).** Mechanism: FFmpeg lavfi filters (`sine`, `testsrc2`) are deterministic *within a pinned build* (the FFmpeg_SHA pin is right), so fixture generation is reproducible. But the wipe→replay→checksum test replays the *log*, so media determinism matters only for generation. The real trap: if the checksum compare is extended to model stages (ASR/OCR/diarization), GPU/thread nondeterminism (faster-whisper on GPU, PaddleOCR, pyannote, splink sampling) produces non-identical outputs run-to-run. Trigger: CI on different runtimes (CPU vs GPU runner, thread counts). Blast radius: flaky CI; worse — a "determinism" claim the team starts to ignore. Mitigation: restrict byte-exact checksums to deterministic stages (segmentation, locator extraction, structural output) and use tolerance-based asserts (WER box, IoU, speaker-label-agnostic diarization metrics) for model stages; lock the lavfi fixture SHA in CI. Also Neo4j graph-export checksums are not order-stable — canonical ORDER BY required. Severity: MEDIUM. Citations: [Tier 3] FFmpeg lavfi filter docs (deterministic sources); [Tier 5] WhisperX eval section re: ASR nondeterminism; engineering-analysis for the rest.

- **R6.2 — lavfi-generated media is too clean to exercise the failure modes the corpus will hit.** Mechanism: sine/testsrc2 lack real-world pathology — VFR, edit lists with negative offsets, damaged containers, out-of-order packets, music-under-speech, corrupt subtitle encodings, archive breakout payloads. ### Final Pattern 1: The Decomposition DAG as Hatchet Durable DAGs, with Semantic-Log Stage Artifacts (addresses R1.1–R1.5, X3, X8)

**Changes from Turn 5:**
- **R1.1/X3 — engine idempotency is best-effort; the log IS the dedup authority (RESOLVED).** Hatchet idempotency is beta with confirmed exactly-once violations: #4129 (non-atomic 3-step scheduled-trigger, wall-clock TTL; fixed #4454 merged 2026-07-17 addressed only the concurrent duplicate-key SQLSTATE 23505 case), #3674 (child-key collision-prone, breaking change planned) ([Tier 1] hatchet-dev/hatchet#4129, #4454, #3674; docs.hatchet.run/v1/idempotency — "in beta and may be subject to change"). Design change: stage-completion records carry `idempotency_key` in their **own log table** `stage_run(idempotency_key TEXT NOT NULL UNIQUE, stage, source_id, run_id, status, payload)` — the `UNIQUE` constraint is Postgres-enforced, independent of the engine. Stage handlers MUST check `stage_run` existence-by-key before performing side effects (handler-level dedup), and append `StageCompleted` only after winning the key insert. Engine collision/DuplicateKey exceptions are caught and the existing run result returned. This is the AWS Durable-Execution rule — at-least-once engine + idempotent consumer = effectively-once ([Tier 1] docs.aws.amazon.com/durable-execution/patterns/best-practices/idempotency/) — applied with the log as the consumer-side authority.
- **R1.2 — pin Hatchet ≥ the merged retry/DAG fixes; regression-test the DAG shapes.** Mitigation: CI pins a Hatchet version ≥ the fix trail (#3860, #1507, #1620, #3243, #4372; check 2026-08-25) and adds regression tests for exactly our shapes: cancel-parent-then-retry, child-cancel-then-parent-fail, replay-after-cancel (cite [Tier 1] hatchet-dev/hatchet#3860/#1507/#1620/#3243/#4372). Temporal fallback triggers from T5 remain the documented exit if these shapes keep breaking.
- **R1.3 — cost-level idempotency is a handler contract, not engine behavior (RESOLVED).** Stage handlers must, on retry, first look up `stage_run` by key and skip re-derivation if artifacts exist; derived per-chunk artifacts are cached in OCFL keyed by (idempotency_key, chunk_id) — re-reading OCFL is still cheaper than re-derivation. Written as a handler contract (checked via the R6 determinism harness), not assumed.
- **R1.4 — audit events do NOT live on the semantic_event replay stream (RESOLVED).** Per-attempt/retry/start/fail audit records go to a **separate `job_run_audit` table** (own seq, not replayed by Tier-1 builders), so replay cost stays proportional to *work*, not *ops*. The semantic log receives one `StageCompleted` per (source, stage) — always evidence-bearing, never per-attempt noise. Batching: a fan-out batch emits one `StageCompleted` with a summary of chunk statuses + `job_run_audit.run_ids[]` refs, not 150k events. This resolves the X3 seq-inflation lag budget without giving up the committed audit guarantee.
- **R1.5 — scale-out path is an operational commitment.** At the T4-honest hundreds/sec Postgres-only baseline, a 36k-chunk fan-out runs in minutes (fine for batch). Written commitment: if ingestion bursts exceed the baseline ≥2× sustained (threshold measured per §33 metrics), the scale-out path (RabbitMQ engines + tuned RDS, the only way Hatchet reaches 10k/s per its guarantees-and-tradeoffs docs) is a funded ops dimension, not an accident.
- **X8 — in-flight version skew (RESOLVED): stage input manifest pinning.** Every stage task's input carries a **manifest** `{stage_schema_version, extractor_version, decoder_version, locator_version, evidence_refs}`. The DAG workflow name includes the stage-schema-version (DAG version namespacing) so a bump creates a new universe; deploy-time drain/cancel: Hatchet queue drain → cancel in-flight runs → wait for quiescence → bump versions. Idempotency keys embed the manifest version, so old keys never collide with new derivations.

**Final shape:** unchanged from T5, plus the `stage_run` UNIQUE-key table, the separate `job_run_audit` table, manifest pinning, pinned Hatchet version, and handler-dedup contract.

### Final Pattern 2: Segment Identity + the `source://` Locator System (addresses R2.1–R2.4, X1, X4)

**Changes from Turn 5:**
- **R2.1/X1 — byte-different re-upload must not orphan locators: `SourceAliased` + work membership (RESOLVED).** New log event `SourceAliased(canonical_source_id, previous_source_id, reason='REUPLOAD|RELEASE_VARIANT|TRANSCODE', work_membership)`; a `works(work_id, canonical_source_id, member_source_ids[], created_seq)` table groups byte-different variants of the same work (§5 continuity). **Override-transfer policy (the design decision T6 demanded):** at ingest of a new variant, every user override / `EntityResolved` / `Aligned` reference anchored to a locator of an existing member is **re-keyed automatically** onto the work-level locator (same structural path, new source id) *by a log record* `LocatorRebased(old_locator, new_locator, override_ids[], reason)`, NEVER by silent in-place editing; any reference whose structural path does not resolve in the new variant (content genuinely changed) is **quarantined** (`quarantine(reference_kind, locator, reason='PATH_UNRESOLVED')`) and surfaced for human decision — never silently dropped. Dedup stays byte-identical-only (OCFL content addressing). §16 selective-rerun runs against the work-level DAG so the "same" episode reruns on its current variant.
- **R2.2 — locator component carries decoder/renderer version (RESOLVED within a fundamental limit).** Add `v=<segmenter_major>.<decoder_major>.<renderer_major>` to the locator: `source://<work_id>/<modality>/<segment_id>@v{...}?frag=...`. `generated_by` records media-decoder + renderer versions (not only model version). A `v` bump triggers a §16 selective-invalidation pass over affected locators. **Fundamental limitation acknowledged:** the EPUB CFI spec itself declares a CFI invalid when its assertions fail and a corrected CFI cannot be derived ("if I add a new `<p>` in the middle, all CFIs pointing to a later paragraph will be wrong" — W3C EPUB-WG minutes, cited by T6), and PDF-render/ffmpeg-demux versions change coordinates ([Tier 3] w3c.github.io/epub-specs/epub33/epubcfi/). Locator stability is therefore *bounded by content stability*, not by our design; the mitigation makes drift **detectable, versioned, and re-runnable**, not impossible.
- **R2.3 — WebVTT `X-TIMESTAMP-MAP` normalization before pysubs2 (RESOLVED).** pysubs2 #34 is open; parsed times ignore the MPEGTS offset. Design change: a **WebVTT pre-normalizer** runs before pysubs2: parse the `WEBVTT` header for `X-TIMESTAMP-MAP=LOCAL:…,MPEGTS:N` (MPEGTS units = 1/90000 s PTS per RFC 8216 §3.5), compute `offset_seconds = MPEGTS/90000 − LOCAL_seconds`, shift every cue's start/end by that offset, strip the header, pass the normalized VTT to pysubs2. Evidence: the issue itself carries the SubtitleEdit implementation; MpegFlow's engineering reference (2026-05-08) documents account-off-by-10-s failures ([Tier 2] mpegflow.com/topics/protocols/hls-x-timestamp-map, 2026-05-08; [Tier 1] brightcove sdks.support; both define the same 90 kHz PTS math). Add an HLS-originated VTT fixture with a nonzero MPEGTS to the §34 matrix (also X4).
- **R2.4 — raw bytes stay the evidence source of truth.** charset-normalizer probe + `errors='surrogateescape'` passthrough for non-UTF-8 subtitles; the OCFL raw subtitle bytes are the evidence anchor; parsed form is a derivation (§2).

**Final shape:** locator grammar gains the `@v{}` version component; log gains `SourceAliased`, `LocatorRebased`, and a quarantine table; work-membership table added; WebVTT pre-normalizer is a mandatory stage before pysubs2.

### Final Pattern 3: State Management — Semantic-Log Schema, Two-Tier Materialization, RYW Token Contract (addresses R3.1–R3.6, X2, X6, X7)

**Changes from Turn 5:**
- **R3.1 — Tier-0 winner-resolution is bounded (RESOLVED).** Winner resolution is **last-write-wins per (entity_ref, predicate)** computed via an indexed `current_state` row-level compare — never a stream scan. A merged entity resolves via a transactionally-maintained `current_entity_map(mention_id → entity_id)` lookup (updated by the same MERGE event), so winner lookups are O(1) reads of the *current* row plus comparison against the incoming event. Explicit bounds: per-event work is O(1) table operations; no full-history pass. Add a §34 burst test: 100k-mention merge churn under concurrent override writes completes within a stated budget (state the budget: ≤5ms p99 Tier-0 path, measured in CI).
- **R3.2/X2 — Tier-0 and Tier-1 are ONE implementation (BLOCKING, RESOLVED).** Both tiers execute the **same pure reduce function** — `reduce_current_state(current_row, event) -> current_row` — defined once in `src/current_state/reducer.py` and imported by (a) the Tier-0 inline writer (called inside the append transaction) and (b) every Tier-1 builder (called during replay per event). No second implementation exists to drift. The §34 determinism test is extended to **rebuild Tier-0 as well**: wipe `current_state` → replay the log → diff the checksum against the pre-wipe copy (KloudVin truncate→replay→diff, carried); and the E2E correction test (below) **asserts Tier-0 and Tier-1 answer equivalence on the corrected entity** (R6.3 folded in). This closes the §40 DoD #34 "inconsistent data across storage technologies" probe at the source.
- **R3.3/X6 — retry amplification and the 503-vs-long-window decision (RESOLVED).** Decision: **both cases are `503`** but distinguished in-band: `Retry-After` short (≤1s) + `x-consistency: transient-lag` for sub-budget lag; `Retry-After` long (≥30s) + `x-consistency: rebuild-in-progress` for scheduled invalidations. A `409`/`425` code class was considered and rejected: 425 has unrelated TLS-early-data baggage, and 409 implies a request conflict the client can fix, which is false here. All token-bearing readers MUST implement exponential backoff + full jitter on 503 (AWS Builder's Library retry-amplification math, cited by T6); server-side waiters use a bounded-concurrency semaphore (never a polling loop per request). A rebuild-in-progress 503 carries an optional `x-rebuild-estimate` header so clients can decide to poll backoff vs fail the call.
- **R3.4/X7 — HNSW: separate append-only embeddings table, never in-place UPDATE (RESOLVED).** pgvector maintainer confirms #875's 100× UPDATE slowdown is expected — "a one-to-one relation would probably work best" ([Tier 1] pgvector/pgvector#875, and #810: update on a table bearing a second m=64 HNSW index collapses QPS; the SO walkthrough shows the split-table + view pattern). Design change: `embedding(segment_id BIGINT PRIMARY KEY REFERENCES segment(segment_id), embedding vector, model_version, created_seq)` — the ONLY HNSW-indexed table; rows are immutable; a new embedding (supersede, evidence_hash bump, model upgrade) = **new row**, never UPDATE. HOT-update-friendly churned metadata stays on `segment` (no vector index co-tenancy). Recall implications documented: `REINDEX INDEX CONCURRENTLY` on scheduled cadence (index-management.org guidance) restores recall after deletions; during rebuild the old index serves reads; autovacuum tuned per-table (scale_factor 0.01–0.05); the §34 determinism harness verifies recall-consistency across rebuilds using the fixture corpus.
- **R3.5 — blue-green schema swap (RESOLVED operationally).** `ALTER SCHEMA ... RENAME` is followed by a no-drop grace period; per-connection `search_path` set at check-out (SQLAlchemy event hook); a swap test in the Pattern 6 harness asserts no pooled connection serves the dropped schema.
- **R3.6 — candidate-set threshold queryability (RESOLVED at design level).** For hot confidence-threshold query paths, store the thresholdable `confidence` as a real numeric column on `current_state` (normalized at write); retain structured JSONB for storage/analysis; GIN remains for rare deep probes. No new index machinery needed.

**Final shape:** single shared `reduce_current_state` reducer; Tier-0 rebuilt in determinism test; 503/Retry-After contract with in-band consistency classes; separate immutable `embedding` table; search_path swap discipline; confidence column normalization.

### Final Pattern 4: Entity Resolution + Alignment (addresses R4.1–R4.4, X5)

**Changes from Turn 5:**
- **R4.1 — splink/DuckDB: pin splink ≥ 4.0.16, do NOT pin DuckDB 1.3 (RESOLVED, evidence-updated).** The DuckDB 1.4.x/1.5.x regression (#2918: 2s→30s+ via wide-CTE materialization + lost column pruning; uk_address_matcher#219 OOM) was **fixed in splink 4.0.16 (2026-03-11)** via re-pipelined SQL (#2961/#2962/#2963/#2966, "Fixed in splink 4.0.16 and merged up to splink_5_dev") ([Tier 1] moj-analytical-services/splink#2918 + CHANGELOG, checked 2026-08-25). Keep: high-cardinality blocking keys (speaker-embedding-cluster id, not raw `speaker_07` labels); chunked prediction (`predict_chunk`/`compute_blocked_pairs_for_predict_chunk`); the resolution stage runs inside a memory-capped sandbox as a bounded batch stage.
- **R4.2 — reproducibility (RESOLVED).** Persist the trained splink model (settings + trained m/u tables) to OCFL as an artifact; fixed seed; incremental linkage = predict-only against persisted model; training cadence is an explicit scheduled job (weekly or at blocking-key schema change), never implicit per-run.
- **R4.3 — Vecalign scope (RESOLVED with acknowledged fundamental limit).** **Fundamental limitation acknowledged:** Vecalign's monotone/contiguous DTW assumptions do not hold for adaptation/non-parallel media (T6's peer-reviewed evidence: Craig & Christodoulopoulos 2023; RASLAN 2021; Nature Sci Rep 2023; Neuralign EACL 2024). Mitigation: Vecalign is **restricted to genuinely parallel text pairs (novel ↔ direct translation) at sentence granularity** and is disabled by default for adaptation/subtitle paths, which use DTW/timecode + embedding-retrieval + LLM reconciliation instead. Every `Aligned` record carries `alignment_source` and a `parallelity_assumption` field (`'PARALLEL_MONOTONE' | 'ADAPTATION' | 'TEMPORAL'`), so consumers can discount confidence appropriately (X5 discipline).
- **R4.4 — SPLIT rebind cascade (BLOCKING, RESOLVED).** Three log-record mechanics:
  1. **MERGE snapshots its mapping.** The `EntityResolved(MERGE, …)` payload stores `mention_to_entity` mapping and every reference kind (`ALIGNMENT`, `OVERRIDE`, `CANDIDATE_SET_MEMBER`, `CLAIM_EVIDENCE`) that points at the merged entity — a replayable snapshot, not a transient.
  2. **SPLIT carries explicit target assignment.** `EntityResolved(SPLIT, old_entity_id, targets[{entity_id, mention_ids[]}], reference_assignments[{reference_id, kind, target_entity_id}], ambiguities[])` — every known reference is explicitly reassigned or declared ambiguous.
  3. **New event type `ReferenceRebound`** records reassignments made after SPLIT: `ReferenceRebound(reference_kind, reference_id, old_entity_id, new_entity_id, source='SPLIT_CASCADE', created_seq)`. References whose target is ambiguous (an `Aligned` edge whose source/target both rode the merged entity, or an override whose meaning under split is contested) are **quarantined** (`quarantine(reference_kind, ..., reason='AMBIGUOUS_SPLIT_TARGET')`) for human decision and surfaced in the §7/§17 response envelope — never silently dropped, never silently left dangling.
  - §34 test (mandatory, mirrors DoD #31): merge → split restores ALL mentions AND all Aligned/override/candidate-set refs to their pre-merge targets, verified by a `ReferenceRebound`-aware determinism diff.

### Final Pattern 5: Error Handling — Sandbox Posture, FFmpeg Boundary, Whisper Hallucination Filter, Archive Extraction (addresses R5.1–R5.6)

**Changes from Turn 5:**

(d) **Confidence re-labeling:** §14 discipline — ASR confidence is stored as **transcription confidence**, never semantic truth; `SemanticAsserted` events derived from ASR carry `derivation='TRANSCRIPTION'` + the filter-signal vector. **Nothing is silently dropped:** filtered segments create a log record `HallucinationFiltered(segment_ref, signals{no_speech_prob, avg_logprob, compression_ratio, acoustic_energy, vad_verdict}, evidence)` — the raw ASR output remains as an untrusted evidence artifact in OCFL; the filter decision is auditable and replayable (§2, §21). Add a music-under-speech + pure-music fixture to the §34 matrix.

**Final shape:** bubblewrap sandbox-runner posture (with sandlock fallback and documented container caps); every FFmpeg/PyAV parse in-sandbox with pinned CVE-fixed versions; 4-stage whisper hallucination filter with `HallucinationFiltered` log records + transcription-confidence labeling; Python ≥ CVE-fixed versions; authority-aware poison policy.
